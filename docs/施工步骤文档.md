# 施工步骤文档（Step-by-Step Build Guide）

> **本文档是"照着做"的执行手册。** 需求见 `需求设计文档.md`，接口契约见 `接口文档.md`，本文档只讲**顺序、产出物、验收标准**。
>
> 核心纪律：**每一步都要能跑、能验证，才进入下一步。** 不允许"改到一半跑不起来"。
>
> **开发方式：垂直切片** —— 后端每做完一个模块，**同步写一个临时 HTML 验证页**，立刻在浏览器里验证接口。前端视觉还原（S10）放到最后，那时接口已冻结，改样式零风险。详见 §0.2。

---

## 0. 使用说明

### 0.1 怎么用这份文档

1. 从上往下做，**不要跳步**（后面的步骤依赖前面的产出）
2. 每完成一个小步骤（如 S1.1），做一次**验收**，通过后勾选
3. 每个阶段结束后 `git commit`，出问题可回滚
4. 遇到报错，先看第 15 章「常见问题」

### 0.2 为什么采用垂直切片（而不是"后端全做完再做前端"）

| | 水平切片（❌ 不采用） | 垂直切片（✅ 采用） |
|---|---|---|
| 做法 | 后端全做完 → 前端全做完 | 登录后端+登录页 → 商品后端+商品页 → … |
| 接口设计错误暴露时机 | 最后集成时才发现 | **写完当阶段立刻发现** |
| 返工量 | 大（两端都要改） | 小（改一个验证页 5 分钟） |
| 中间可演示性 | 到 70% 还是"只有接口能跑" | **每个阶段都能演示完整功能** |
| 方向感 | 长时间看不到成果 | 每 1~2 天看到一个能跑的页面 |

**工业界的敏捷开发主流就是垂直切片。** 本项目的阶段划分已按此重排：**每个后端阶段都配一个同步的验证页**。

### 0.4 关键顺序说明：为什么登录页必须早做

**S3 的登录页是整个项目里唯一一个"提前做成正式版"的前端页面。** 原因：

> 后面**所有**接口都需要 `Authorization: Bearer <token>`。
> 如果 S3 就把登录跑通、token 存进 `localStorage`，那 S4~S9 的所有验证页都能**直接复用这个 token**，不用每次手动塞。

这个顺序能省掉大量重复劳动 —— 否则每个验证页都要自己处理一次登录、自己存一次 token。

### 1.4 编码约定

| 场景 | 约定 |
|------|------|
| 统一响应 | 所有接口返回 `Result<T>`（`code`/`message`/`data`） |
| 业务异常 | 抛 `BusinessException`，由 `GlobalExceptionHandler` 统一转 400 |
| 事务 | 加在 **Service 层**，不在 Controller |
| 状态码 | 用**枚举**（`ProductStatus` / `BehaviorType`），禁止魔法数字 |
| 密码 | **BCrypt**，禁止明文 |
| SQL | 参数化，禁止字符串拼接；分页必须装 `PaginationInnerInterceptor` |
| 日志 | 用 `@Slf4j`，禁止 `System.out.println`（参考项目到处是 `println`，是反面教材） |
| 密码字段 | **任何响应中都不得包含 `password`** |

```

2. 写后端代码（小步：实体 → Mapper → Service → Controller）

4. 写/更新本阶段的验证页（frontend/public/verify/sN-xxx.html）
```

### 1.6 验证页约定（**重要**）

> ⚠️ **本节是历史约定，已于 S10 终结**：`frontend/public/verify/` 目录**已删除**（原因见 §11 S10.4）。
> 现在所有功能都在正式页面（`frontend/src/views/`）里，自动化断言在 `scripts/e2e-test.mjs`。
> 保留下面的内容，是为了说明"垂直切片阶段"当时是怎么做验证的。

每个后端阶段配一个**临时静态 HTML 验证页**，放在 `verify/` 目录。

#### 1.6.1 为什么用静态 HTML 而不是 Vue

| | 静态 HTML 验证页（✅ 采用） | Vue 调试页（❌ 不采用） |
|---|---|---|
| 成本 | 每个接口 **2~5 分钟** | 每个页面 **1~2 小时** |
| 改接口时 | 直接重写，不心疼 | 要改组件、props、路由 |
| 看 JSON | 原文直接显示 | 要展开控制台 |
| 到 S10 时的状态 | **直接删掉** | 变成"没样式但结构已定死"的技术债 |

> 💡 **验证页是消耗品，不是资产。** S10 做完视觉还原后，`verify/` 目录可以整个删掉。
> 如果现在就用 Vue 搭"不加样式的正式页面"，到 S10 想改布局时，会发现一堆组件都要重写 —— **省下的时间会加倍还回去**。

### 1.7 开发调试开关（`app.review.enabled`）

**问题**：正式流程是「发布 → 待审核 → 管理员通过 → 才出现在前台」。
开发时想测收藏 / 咨询 / 卖家主页，每换一件测试数据都要**切管理员账号审核一次**，非常碍事。

**做法**：加一个「发布是否需要审核」的开关（`com.secondhand.config.ReviewSwitch`）。

| 值 | 发布后的 `status` | 用途 |
|:--:|:-----------------:|------|
| `true`（默认） | 0 待审核 | 正式行为 |
| `false` | 1 在售 | 仅本地测试 / 演示，发布即可见 |

**两种改法**（任选其一）：

| 方式 | 怎么做 | 要重启吗 |
|------|--------|:--------:|
| ① 配置文件 | `application.yml` → `app.review.enabled: false` | 要 |
| ② 后台在线切换 | 后台「商品审核」页顶部的按钮，或 `PUT /api/admin/settings/review?enabled=false` | **不用** |

**三条约束（别踩）**：

| 约束 | 原因 |
|------|------|
| 只影响**初始状态**，不跳过其他校验 | 测试模式不该让"没填微信也能发布""挂一级分类"这类规则失效 |
| 运行时切换**只存内存**，重启回到配置值 | 免得某次调试忘了关，第二天启动还以为在正式模式 |
| 启动日志会**显眼打印**当前模式 | 同上；另外 `curl /api/health` 也能看到 `reviewEnabled` |

> 💡 字段用了 `volatile`：Tomcat 多线程读这个布尔值，一个线程改、几十个线程读，
> `volatile` 保证改完别的线程立刻看得见（否则会出现"点了开关没反应"这种诡异现象）。

> ⚠️ **`category.name` 上有 `uk_name` 全局唯一索引** —— 不只是同级不重名，
> 而是**全库**都不能重名。所以不能出现两个叫"其他"的二级分类，
> 二级名也不能和一级名撞车（例如一级叫"图书文具"，二级就不要再叫"文具图书"）。

**实现要点**：

- 一级分类 `parent_id = NULL`，二级分类 `parent_id` 指向一级分类 id
- **不能用硬编码 id 写二级分类的 parent_id**（参考项目的教训：前端硬编码 `156`/`164` 全是错的）
- 推荐写法：先插一级，再用 `SET @pid = (SELECT id FROM category WHERE name='数码电子' AND parent_id IS NULL);` 然后插二级
- 幂等做法：`INSERT ... AS new ON DUPLICATE KEY UPDATE parent_id = new.parent_id, sort_order = new.sort_order`
  （`AS new` 是 MySQL 8.0.19+ 的行别名语法，替代已废弃的 `VALUES(col)`)
- **不要用 `DELETE FROM category` 来重置** —— `fk_product_category` 是 `ON DELETE SET NULL`，
  删分类会把已有商品的分类一起清空。用 `ON DUPLICATE KEY UPDATE` 才对。

**验收**：
```sql
SELECT COUNT(*) FROM category;                          -- 50（9 + 41）
SELECT COUNT(*) FROM category WHERE parent_id IS NULL;  -- 9
SELECT p.name AS parent, c.name AS child
FROM category c JOIN category p ON c.parent_id = p.id LIMIT 10;  -- 父子对应正确
```

> 💡 **两个实现细节（比"随机"更好）**
> 1. **不要用 `RAND()`** 生成浏览量/发布时间 —— 那样每次重跑数据都变，排查问题时
>    你会分不清"这是 bug 还是数据变了"。改用**确定性公式**：

>    ⚠️ `product` 被外键引用，`TRUNCATE` 前必须先 `SET FOREIGN_KEY_CHECKS = 0;`。

#### S1.4.3 收藏数据 + 行为数据

**必须保持一致**，否则 S7 阶段测试时数据会对不上：

1. 先插 `favorite` 记录（buyer01 / buyer02 各收藏若干）
2. 再按 `favorite` 表实际数量**更新** `product.favorite_count`：
```sql
UPDATE product p SET favorite_count = (
    SELECT COUNT(*) FROM favorite f WHERE f.product_id = p.id
);
```
3. 插入 `user_behavior` 记录（浏览/收藏/咨询），咨询记录用于验证 S6 的「N 人想要」

**实际做法**：

```sql
-- 收藏用 INSERT IGNORE + SELECT：撞上 uk_user_product 就跳过，天然幂等
INSERT IGNORE INTO favorite (user_id, product_id, create_time)
SELECT @u_b1, p.id, DATE_SUB(NOW(), INTERVAL MOD(p.id * 3, 25) DAY)
FROM product p
WHERE p.status IN (1, 2)
  AND p.seller_id <> @u_b1      -- ← 不能收藏自己的商品（BR-F-1）
ORDER BY MOD(p.id * 17, 101) DESC
LIMIT 18;

-- 行为表【没有唯一键】（同一人能浏览同一商品多次），所以没法 IGNORE，直接清空重插
DELETE FROM user_behavior;
```

| 行为类型 | 条数 | 怎么来的 |
|:--------:|:----:|----------|
| 1 浏览 | 103 | `user CROSS JOIN product`，用 `MOD(商品id * 用户id, 5) = 0` 挑一部分 |
| 2 收藏 | 47 | **直接从 `favorite` 表派生**（时间也照搬）→ 保证行为表与收藏表永远对得上 |
| 3 咨询 | 16 | 从收藏里挑一部分（buyer01/buyer02 中 `MOD(id,2)=1` 的），时间 +2 小时 |
| 4 取消收藏 | 3 | buyer02 对 3 件「已下架」商品取消收藏 —— 数据自洽：卖家下架了，买家不想要了 |

> 💡 **两个设计要点**
> 1. **收藏人 / 购买人 / 卖家都可以是同一个用户**（本项目不分买卖角色），
>    唯一限制是**不能收藏自己发布的**。种子数据用 `seller_id <> 自己` 过滤，实测 0 条违规。
> 2. **行为表 type=2 的行数必须等于 `favorite` 表行数**（都从同一份数据派生）。
>    如果不等，说明中间被人删过收藏但没记行为 —— 真实业务里也要注意这个一致性。

> 💡 **为什么强调"保持一致"**：`favorite_count` 是**冗余字段**。如果种子数据里它和 `favorite` 表对不上，后面取消收藏时 `-1` 就会出现负数，调试时会很困惑。

**验收**：
```sql
USE secondhand_shop;
SELECT COUNT(*) FROM user;          -- 6
SELECT COUNT(*) FROM category;      -- 50（9 + 41）
SELECT COUNT(*) FROM product;       -- 66
SELECT status, COUNT(*) FROM product GROUP BY status;   -- 5 种状态都有（7/46/7/3/3）
SELECT COUNT(*) FROM favorite;      -- 47，与 product.favorite_count 之和一致
SELECT behavior_type, COUNT(*) FROM user_behavior GROUP BY behavior_type;  -- 1/2/3/4 四种都有
SELECT behavior_type, COUNT(*) FROM user_behavior GROUP BY behavior_type;

-- 一致性检查：应为 0 行不一致
SELECT p.id, p.favorite_count, COUNT(f.id) AS real_count
FROM product p LEFT JOIN favorite f ON f.product_id = p.id
GROUP BY p.id, p.favorite_count HAVING p.favorite_count <> real_count;
```

### S3.4 注册（**BCrypt**）

### S3.5 登录（BCrypt 校验）

**流程**：

### S6.2 ⭐ 标为已售出（乐观锁）

**产出**：`PUT /api/products/{id}/mark-sold`

**这是本项目唯一的并发点。**

**实现要点**：

```java
// ❌ 错误写法（参考项目的做法）：先查再改，中间有并发窗口
Product p = getById(id);
if (p.getStatus() == 1) { p.setStatus(2); updateById(p); }   // 可能重复执行

// ✅ 正确写法：用条件 UPDATE，靠数据库保证原子性
int rows = productMapper.update(null,
    new LambdaUpdateWrapper<Product>()
        .eq(Product::getId, id)
        .eq(Product::getStatus, 1)          // ← 关键条件
        .set(Product::getStatus, 2));

if (rows == 0) {
    throw new BusinessException("商品已非在售状态");
}
```

**校验**：
- 必须是商品所有者 → 否则 403
- 乐观锁影响行数为 0 → 400

| 要点 | 说明 |
|------|------|
| 不可逆 | 标为已售后**不能改回在售**（BR-T06）。前端二次确认 |
| 事务 | 用 `@Transactional(rollbackFor = Exception.class)`，注解加在 **Service 层** |

> ⚠️ **参考项目的 bug**：`OrderController:358` 的 `checkBookLock()` 只是"重新查一次状态"，注释里自己承认"可结合 Redis 分布式锁"。**这不是加锁**，存在竞态。

> 💡 **为什么后台统计用 10 条 `COUNT(*)` 而不是一条大 SQL**：
> 这是后台首页的一次性请求，不是高频接口。为了省 9 次查询把 SQL 拼成
> 一条看不懂的 `SUM(CASE WHEN ...)` 大语句，以后再想加一个指标就得重写整条语句。
> 真要优化，该做的是加 Redis 缓存（S12 的思路），而不是把 SQL 玩花。

> 💡 **为什么"强制下架"和 C 端"下架"是两个接口**：
> 唯一的区别是**归属校验** —— C 端必须先证明"这件商品是你发的"，
> 后台故意不做这个校验（管理员就是要能下架任何人的违规商品）。
> 但"必须是 `status=1` 在售"这条校验两边都保留：已售出不能改成已下架（那是篡改历史）。

> 💡 **禁用为什么要立刻生效**：
> JWT 是无状态的，token 一旦签发，服务端"记不住"它被吊销了。
> 本项目在 `OptionalAuthInterceptor` 里**每个请求都查一次库**确认 `status`，
> 所以禁用后旧 token 立刻 401。代价是每请求多一次主键查询，

### S12.1 Redis 三个场景

| 场景 | 做法 | 证据 |
|------|------|------|

## 14. 阶段 S13：站内聊天（轮询版）

> **目标**：用站内聊天替代"暴露联系方式"，解决隐私问题。

### S13.1 数据层（与 WebSocket 版完全一致）

| 表 | 字段 |
|----|------|
| `conversation` | id, user_a_id, user_b_id, product_id, last_message, last_time, create_time |
| `message` | id, conversation_id, sender_id, content, is_read, create_time |

**要点**：
- 会话用 `(user_a_id, user_b_id)` 唯一约束，**约定 `user_a_id < user_b_id`** 避免重复会话
- `conversation` 关联 `product_id`（同一对用户就不同商品可以有多个会话）

### S13.2 接口（5 个）

| 接口 | 说明 |
|------|------|
| `POST /api/chat/conversations` | 创建/获取会话（传对方 userId + productId） |
| `GET /api/chat/conversations` | 我的会话列表（含未读数） |
| `GET /api/chat/messages?conversationId=&afterId=` | **拉新消息**（轮询用） |
| `POST /api/chat/messages` | 发消息 |
| `PUT /api/chat/conversations/{id}/read` | 标记已读 |

### S13.3 前端

- 聊天组件：消息列表 + 输入框
- `setInterval` 每 3 秒拉一次新消息（用 `afterId` 增量拉取，**不要每次全量拉**）
- 组件卸载时 `clearInterval`（否则会内存泄漏）

### S13.4 升级到 WebSocket（可选）

**数据层完全不用改**，只替换推送层。难点：
1. WebSocket 握手拿不到 JWT（浏览器 API 不支持自定义头）→ token 放 query 参数
2. 连接管理：`Map<userId, Session>`
3. 离线消息：必须落库，上线补推

## 15. 常见问题（踩坑记录）

| 问题 | 原因 | 解决 |
|------|------|------|
| **编译报大量"找不到符号"** | JDK 23+ 关闭注解处理 + Lombok 版本过低 | pom 加 `<proc>full</proc>` **且** Lombok 升到 1.18.44（**两条都要**） |
| **`Unknown column 'xxx'`** | 实体字段与数据库列名不一致 | 检查 `map-underscore-to-camel-case`；下划线列名 ↔ 小驼峰字段 |
| **分页失效（返回全表）** | 未注册分页插件 | 注册 `PaginationInnerInterceptor`（**不报错但结果错**） |
| **`user` 表 SQL 报错** | `user` 是 MySQL 保留字 | SQL 中写 `` `user` `` |
| **联系方式无需登录就能拿到** | 拦截器把 `/api/products/**` 整体放行了 | 白名单要精确，或在接口内显式校验 |
| **`.ps1` 中文乱码** | PowerShell 5.1 按 ANSI 读无 BOM 文件 | 脚本存为 **UTF-8 with BOM** |
| **`-h127.0.0.1` 报主机名错误** | PowerShell 把 `.0.0.1` 当属性访问 | 加引号写 `"-h127.0.0.1"` |
| **`favorite_count` 变负数** | 重复取消收藏 | 取消时用 `favorite_count = GREATEST(favorite_count - 1, 0)` |
| **两个项目端口冲突** | 参考项目用 8080/5173 | 我们用 **8081/5174** |
| **改完 `.ps1` 就报"字符串缺少终止符"** | 编辑工具重写文件时**丢掉了 BOM** | 编辑 `.ps1` 后必须重新加 BOM，见 §15.1 |
| **`mysql` 里 `-h127.0.0.1` 变成 host=`127`** | PowerShell 把 `-h127` 当参数名解析 | 用**参数数组** `& $mysql @argList` 传参，不要拼成一行 |
| **`TRUNCATE` 报 `Cannot truncate a table referenced in a foreign key`** | 该表被别的表用外键引用 | 先 `SET FOREIGN_KEY_CHECKS = 0;`，TRUNCATE 完再设回 `1` |
| **`db-init.ps1` 导入顺序错乱** | 旧版按 `user`/`book` 等关键词匹配文件名 | 已修：数字前缀（`01_`/`02_`）按文件名升序；`99_*.sql` 自动跳过 |
| **`INSERT ... VALUES ... AS new` 报语法错** | `AS new` 行别名需要 MySQL **8.0.19+** | 本项目用 8.0.43，可用；若换低版本要改回 `VALUES(col)` |
| **导入 SQL 后中文注释/数据变问号** | 客户端连接字符集不是 utf8mb4 | 加 `--default-character-set=utf8mb4`（`Invoke-Sql` 已带） |
| **接口返回的时间是 `2026-09-22T19:43:10`** | `spring.jackson.date-format` 只对老的 `java.util.Date` 生效，**管不了 `LocalDateTime`** | 加 `JacksonConfig` 注册 `LocalDateTimeSerializer` / `LocalDateTimeDeserializer`（S2 已加） |
| **接口把 `phone` / `wechat` / `qq` 返回出去了** | 直接把实体类当响应体返回 | 这三个字段加 `@JsonIgnore`（**默认永不序列化**），需要展示时用专门 VO 显式带出 |
| **Maven 控制台里中文变乱码** | JDK 18+ 的 `System.out` 默认按 UTF-8 输出，Windows 控制台按 GBK 解码 | 启动横幅改用英文；或用 `java -Dfile.encoding=GBK`（推荐前者，一劳永逸） |
| **`allowedOrigins("*")` 启动直接报错** | 它不能和 `allowCredentials(true)` 共存 | 改用 `allowedOriginPatterns("*")`（注意是 **Patterns**） |
| **业务错误返回的是 HTTP 200，body 里才是 400** | `@RestControllerAdvice` 的方法返回 `Result` 时，HTTP 状态码默认是 200 | 返回 `ResponseEntity.status(...)`，让 **HTTP 状态码 = body.code**（S3 已统一） |
| **把实体直接当响应返回，联系方式漏出去了** | 实体字段默认全部序列化 | 敏感字段标 `@JsonIgnore`；要展示时用 VO 显式带出。**默认拒绝比默认放行安全** |
| **`file://` 打开的验证页读不到登录页的 token** | `localStorage` 按源隔离，`file://` 和 `localhost:5174` 是两个源 | 验证页放 `frontend/public/verify/`，通过 `http://localhost:5174/verify/xxx.html` 访问 |
| **Vite 启动刷一堆 `Failed to run dependency scan`** | 它把 `public/verify/*.html` 也当成入口去扫描了 | 在 `vite.config.js` 里配 `optimizeDeps: { entries: ['index.html'] }` |
| **`require is not defined`（写 `.mjs` 脚本时）** | ESM 模块里没有 `require` | 用 `import { xxx } from 'node:fs'`；顺带注意**顶层不能条件导入** |
| **公开接口里拿不到登录用户**（`canContact` 永远说"请先登录"） | 路径在拦截器白名单里 → **拦截器根本不执行** → `UserContext` 是空的，登录的人也被当成游客 | 拆成两个拦截器：`OptionalAuthInterceptor`（拦所有 `/api/**`，认得出身份就记下，认不出当游客，**永不拒绝**）+ `JwtInterceptor`（只拦非白名单路径，检查有没有身份）。用 `.order(1)` / `.order(2)` 固定顺序（S4 已实现） |
| **浏览量 +1 之后「更新时间」也跟着变了** | `update_time` 列是 `ON UPDATE CURRENT_TIMESTAMP`，这行数据一被改动就自动刷新 | SQL 里显式写 `update_time = update_time` —— MySQL 的规则是"只要语句里显式写了这一列，就不再使用自动值" |
| **PowerShell 里 `foreach ($pid in ...)` 报"无法覆盖只读变量"** | `$pid`、`$host`、`$args`、`$input` 等是 PowerShell 内置只读变量 | 换个名字（如 `$prodId`）。这类报错信息很有迷惑性，看着像语法问题 |
| **`GET /api/products/abc` 返回 500** | 路径变量要转 Integer，"abc" 转不过去，异常没被专门处理，落到兜底 Exception | 加 `MethodArgumentTypeMismatchException` handler → 400（这是客户端的错，不是服务器故障） |
| **上传成功，但访问图片 URL 是 404** | "写文件的目录"和"静态资源映射的目录"各自算了一遍，两边不一致 | 抽出 `UploadStorage` 作为唯一来源，`UploadController` 和 `WebConfig` 都从它取 |
| **测试脚本里写死 `categoryId: 4` 结果发布被拒** | id=4 实际是**一级分类**"服饰鞋包"，不是预想中的二级分类"耳机" | 分类 id 一律从 `/api/categories` 动态取 —— 这正是本项目反复强调的"不硬编码 id" |
| **在浏览器里 fetch 上传图片返回 401** | 手写的 fetch 忘了带 `Authorization` 头（页面里封装好的 `uploadFile()` 是带的） | 直接调封装函数；或在 fetch 的 headers 里补上 token |

### 15.1 修复 `.ps1` 的 BOM（编辑后必做）

```powershell
# 把 scripts 下所有 .ps1 重新存为 UTF-8 with BOM（幂等，可随时跑，已有 BOM 的会保持）
Get-ChildItem scripts -Filter '*.ps1' | ForEach-Object {
    $t = [System.IO.File]::ReadAllText($_.FullName, (New-Object System.Text.UTF8Encoding($false)))
    [System.IO.File]::WriteAllText($_.FullName, $t, (New-Object System.Text.UTF8Encoding($true)))
}
```

> 症状长这样：`The string is missing the terminator: '.` 或 `Missing closing '}' in statement block.`
> 看着像括号写错了，**其实是编码问题** —— 中文被按 GBK 解码后字节错位，把引号"吃掉"了。
> 记住一句话：**看到 `.ps1` 报奇怪的语法错，先怀疑 BOM，别怀疑括号。**

### 15.2 生成 BCrypt 密文（不依赖 Java）

S1 阶段还没有 Spring Security 依赖，用 Node 的 `bcryptjs` 生成（纯 JS，免编译）：

```powershell
$d = Join-Path $env:TEMP 'bcrypt-gen'
New-Item -ItemType Directory -Force -Path $d | Out-Null
Push-Location $d
npm install bcryptjs --silent --no-audit --no-fund
node -e "const b=require('bcryptjs');['admin123','123456'].forEach(p=>console.log(p,'=>',b.hashSync(p,10)))"
Pop-Location
```

> 装在 `%TEMP%` 下，**不会污染项目目录**（项目里不需要 `package.json`）。
> 生成的是 `$2b$10$` 60 字符密文，与 Spring Security 兼容。
