## 1. 业务背景与目标

### 1.1 项目定位

面向**高校校园**的二手商品交易平台。学生在平台上发布闲置物品，其他学生浏览、购买，**线下当面交易**（校内见面交付，不走物流）。

### 1.2 与原参考项目的本质区别

| 维度 | 参考项目（智循书堂） | 本项目 |
|------|---------------------|--------|
| 商品类型 | 只有教材（有 ISBN、作者、出版社） | **全品类二手商品**（数码/家电/服饰/运动…） |
| 库存模型 | 有多库存字段（但代码没实现扣减） | **纯单品制**：一件商品 = 一条记录 |
| 交易方式 | 邮寄（有收货地址） | **校园当面交易**（有交易地点） |
| 议价 | 无 | 无（一口价） |
| 交易达成 | 平台内下单+支付+发货 | **信息撮合**：平台只促成联系，交易线下完成 |
| 互动 | 几乎为零 | **收藏（想要）+ 行为埋点 + 卖家主页** |
| 前端 | 通用 Element Plus 蓝色风格 | **仿闲鱼黄色视觉**，自定义样式 |

> ⚠️ 因此**不能复用原项目的表结构**。本项目表结构从业务属性重新推导（见第 5 章）。

### 1.3 学习与交付目标

- **学习目标**：掌握 Spring Boot 分层架构、MyBatis-Plus、JWT 鉴权、Redis 缓存（后期）、AI 服务集成（后期）
- **交付物**：可运行系统 + 实验报告 + 答辩 PPT + 演示视频

## 3. 角色与权限

### 3.1 角色定义

**只有两种角色**（简化于闲鱼的"人人可买卖"模型）：

| 角色 | 说明 | 权限范围 |
|------|------|----------|
| **游客**（未登录） | 无账号访问者 | 浏览商品列表、商品详情、卖家主页、分类 |
| **user** | 注册用户，**既可买也可卖** | 游客权限 + 发布商品、下单、收藏、查看自己的订单与商品 |
| **admin** | 管理员 | 全部权限 + 审核商品、下架商品、管理用户、查看全量数据 |

> 🔑 **关键设计**：不区分"买家/卖家"角色。同一个 `user` 发布商品时是卖家、下单时是买家，**身份由行为决定**。
> 参考项目的 `role` 里有 `seller` 值，本项目**取消**。

### 3.2 权限矩阵

| 功能 | 游客 | user | admin |
|------|:----:|:----:|:-----:|
| 浏览商品列表/详情 | ✅ | ✅ | ✅ |
| 搜索/筛选/排序 | ✅ | ✅ | ✅ |
| 查看卖家主页 | ✅ | ✅ | ✅ |
| 注册/登录 | ✅ | — | — |
| 发布商品 | ❌ | ✅ | ✅ |
| 立即购买 | ❌ | ✅ | ✅ |
| 收藏/取消收藏 | ❌ | ✅ | ✅ |
| 我的订单/我发布的/我的收藏 | ❌ | ✅ | ✅ |
| 编辑/下架自己的商品 | ❌ | ✅ | ✅ |
| 商品审核/下架他人商品 | ❌ | ❌ | ✅ |
| 用户管理（禁用/启用） | ❌ | ❌ | ✅ |
| 数据统计 | ❌ | ❌ | ✅ |

### 3.3 鉴权实现

- **认证**：JWT。登录成功返回 token，前端存 `localStorage`，后续请求带 `Authorization: Bearer <token>`
- **拦截器**：`JwtInterceptor` 校验 token → 把 `userId/username/role` 放进 request attribute
- **上下文**：`UserContext.getCurrentUserId()` 供 Service 层取当前用户
- **管理员**：`AdminInterceptor` 校验 role 是否为 admin
- **密码**：BCrypt 加密存储（**修正参考项目的明文密码缺陷**）

## 4. 核心业务流程

### 4.1 商品生命周期

```
              [卖家发布]
                  ↓
   ┌─────────── status = 0 待审核 ───────────┐
   │                                          │
[管理员通过]                            [管理员拒绝]
   ↓                                          ↓
status = 1 在售                          status = 4 已拒绝
   │
   ├──────────────[卖家主动下架]──────────────→ status = 3 已下架
   │
   └──────────[卖家确认交易完成]──────────────→ status = 2 已售出
```

**状态枚举**：

| 值 | 名称 | 说明 |
|:--:|------|------|
| 0 | 待审核 | 刚发布，仅自己和管理员可见 |
| 1 | 在售 | 已上架，所有人可见、可预定 |
| 2 | 已售出 | **卖家确认交易完成**后置为此状态，不可再预定 |
| 3 | 已下架 | 卖家主动下架 |
| 4 | 已拒绝 | 管理员审核不通过 |

> 参考项目的 bug：「下架」接口把 status 写成了 2（与"已售出"混用）。本项目的 3 专门表示"已下架"。

### 4.2 交易模型：**信息撮合，平台不碰钱** ⭐

这是本项目**最重要的设计决策**，需要先讲清楚。

#### 4.2.1 为什么不设计"平台担保"

最初的设想是照搬电商：付款 → 平台托管 → 确认收货 → 打款给卖家。但在本项目约束下（**不做钱包、不做聊天、不做评价、不做邮寄**），这套设计**站不住脚**：

| 问题 | 说明 |
|------|------|
| 平台根本没有真实资金 | "已付款"只是改了个状态位，**"退款"无从谈起**，因为从没扣过钱 |
| 无交付凭证 | 没有物流单号、没有聊天记录，**平台无法仲裁"到底交付了没有"** |
| 无信任机制 | 没有评价体系，买卖双方的履约意愿没有任何约束 |

**结论**：任何"平台担保"设计都是假的，还会引入一堆无法自圆其说的分支（如"卖家没交付但买家点了确认"该怪谁）。

#### 4.2.2 本项目的方案

**平台只做撮合，交易在线下自行完成。**

```
┌──────────────────────────────────────────────────────────┐
│  平台负责（系统内）          │  用户自己负责（线下）        │
├──────────────────────────────┼───────────────────────────┤
│  · 商品展示与搜索            │  · 见面交付商品             │
│  · 产生一条"预定记录"        │  · 当面付钱（现金/微信转账） │
│  · 交换双方联系方式          │  · 验货、议价（线下自行商量）│
│  · 记录"已完成/已取消"       │  · 任何纠纷自行协商         │
└──────────────────────────────┴───────────────────────────┘
```

**平台从始至终不涉及金额计算、不托管资金、不提供退款。**

**支付方式字段的作用**：结算页让买家选"支付宝/微信"，**仅用于提示双方线下用什么方式付款**，不产生任何实际交易记录。

#### 4.2.3 订单生命周期（两态 + 取消）

```
[买家点"立即购买"]
        ↓
  status = 0 待交易 ──────[买家取消]──────→ status = 4 已取消
        │
  [双方看到联系方式，线下见面交易]
        │
  [卖家点"确认已交易"]
        ↓
  status = 3 已完成（商品同时变为已售出）
```

**状态枚举**：

| 值 | 名称 | 说明 |
|:--:|------|------|
| 0 | 待交易 | 订单已创建，双方可见联系方式 |
| 3 | 已完成 | **卖家**确认交易完成（商品置为已售出） |
| 4 | 已取消 | 订单作废（买家可取消；也可由卖家拒绝） |

> **说明**：
> - **不存在"已付款(1)"状态** —— 平台不处理支付，没有这个环节。
> - `2`（已发货）在参考项目中存在，本项目不做邮寄，**不产生 2**。
> - 编号保留 0/3/4，方便与参考项目对照学习。

#### 4.2.4 谁有权确认完成？

**由「卖家」确认**，而不是买家。理由：

- 卖家是交付商品的一方，**"我东西交出去了"这件事卖家最清楚**
- 若由买家确认，会出现"买家拿到了却不点确认"的扯皮
- 卖家确认后商品自动置为"已售出"，**卖家有动力及时确认**（早点下架，不再被其他人询问）

**防刷单/防恶意**：买家可取消订单；若买家恶意下单（占用商品不交易），卖家可在"我卖出的"列表里**拒绝该订单**（同样置为已取消）。

### 4.3 下单主流程（时序）

```
买家                 前端                  后端                      数据库
 │                商品详情页
 │──点"立即购买"──→ 结算页
 │                （显示商品 + 交易地点 + 联系方式）
 │──选支付方式────→ POST /api/orders {productId}
 │                ←────────────────────── OrderController.create()
 │                                       ├ 校验商品 status=1
 │                                       ├ 校验不是自己买自己
 │                                       ├ 校验该商品无进行中订单
 │                                       └ INSERT order(status=0)
 │                ←── 返回订单（含卖家联系方式）
 │
 │──【下单成功页】───────────────────────→ 显示：卖家昵称 + 手机号
 │   （双方此时可互相联系，约时间地点）
 │
 │──线下见面，付钱拿货（平台不参与）─────→
 │
卖家                 前端                  后端
 │──点"确认已交易"→ PUT /api/orders/{id}/complete
 │                ←────────────────────── OrderController.complete()
 │                                       ├ 校验订单归属（是卖家本人）
 │                                       ├ 乐观锁: UPDATE product SET status=2
 │                                       │         WHERE id=? AND status=1
 │                                       └ UPDATE order SET status=3
 │                ←── "交易完成"
```

**并发安全**：确认完成时用**乐观锁**（`UPDATE product SET status=2 WHERE id=? AND status=1` 判断影响行数），防止一个商品被多个订单同时标记售出。
> 参考项目的 `checkBookLock()` 只是重新查一次状态，**没有真正加锁**，存在超卖风险。

**为什么还要保留订单表？**
即使平台不碰钱，订单表仍承担三个不可替代的作用：
1. **让卖家知道"谁想要了我的东西"**（否则无从联系）
2. **让商品能自动变为"已售出"**（否则要卖家手动维护）
3. **给个人中心提供「我买到的 / 我卖出的」两个 Tab 的数据源**

### 5.5 `product_order` 订单表（**预定记录**，非资金订单）

> ⚠️ 本表**不记录资金流向**，只记录"谁想要了哪个商品、最后成没成"。详见 §4.2 交易模型。

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| id | int | PK, AUTO | 订单ID |
| order_no | varchar(50) | NOT NULL, UNIQUE | 订单号（时间戳+UUID） |
| buyer_id | int | NOT NULL, FK→user.id | 买家ID |
| seller_id | int | NOT NULL, FK→user.id | 卖家ID（下单时快照） |
| product_id | int | NOT NULL, FK→product.id | 商品ID |
| product_title | varchar(100) | NOT NULL | **商品标题快照**（商品被删也不影响订单） |
| product_image | varchar(255) | | **商品主图快照** |
| price | decimal(10,2) | NOT NULL | **商品价格快照**（仅用于展示，平台不据此收钱） |
| status | tinyint | DEFAULT 0 | **0待交易 / 3已完成 / 4已取消** |
| pay_method | varchar(20) | | **线下支付方式意向**：alipay / wechat / cash |
| trade_place | varchar(100) | | **交易地点快照** |
| buyer_remark | varchar(255) | | 买家备注 |
| finish_time | datetime | | 完成时间 |
| cancel_time | datetime | | 取消时间 |
| cancel_reason | varchar(255) | | 取消原因 |
| create_time | datetime | DEFAULT now | 下单时间 |

**删除的字段**：
- `address_name`/`address_phone`/`address_detail` —— 不做邮寄
- `pay_time` —— **平台不处理支付**，没有"付款时间"这个概念

**唯一的业务约束**：同一商品**同时只能有一个"待交易"订单**（避免多个买家重复预定同一件商品）。

> 💡 **快照设计**：`product_title`/`price`/`trade_place` 存的是**下单瞬间的副本**。这样即使卖家改了价格或删了商品，历史订单依然显示当时的真实信息 —— 这是交易系统的标准做法，也是**不可变记录**思想的体现。
>
> 💡 **为什么保留 `price` 字段**：平台虽然不收钱，但订单里必须有价格，否则"我买到的"列表无法展示历史成交价。这个价格是**记录**，不是**结算依据**。

### 5.6 `favorite` 收藏表（新增）

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| id | int | PK, AUTO | |
| user_id | int | NOT NULL, FK→user.id | 收藏人 |
| product_id | int | NOT NULL, FK→product.id | 被收藏商品 |
| create_time | datetime | DEFAULT now | 收藏时间 |

**唯一约束**：`UNIQUE KEY (user_id, product_id)` —— 防止重复收藏。

### 5.7 `user_behavior` 行为表

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| id | int | PK, AUTO | |
| user_id | int | NOT NULL | 用户ID |
| product_id | int | NOT NULL | 商品ID |
| behavior_type | tinyint | NOT NULL | **1=浏览 / 2=收藏 / 3=购买** |
| behavior_time | datetime | DEFAULT now | 行为时间 |

**索引**：`(user_id)`、`(product_id)`、`(behavior_type)`

## 6. 业务规则

### 6.1 商品规则

| 编号 | 规则 |
|------|------|
| BR-P01 | 商品标题 5~100 字符，必填 |
| BR-P02 | 价格必须 > 0，最多两位小数 |
| BR-P03 | 原价可选；若填写，必须 ≥ 现价 |
| BR-P04 | 图片最多 9 张，格式 JPG/PNG/GIF/WebP，单张 ≤ 5MB |
| BR-P05 | 成色取值限定：`全新` / `几乎全新` / `轻微使用痕迹` / `明显使用痕迹` |
| BR-P06 | 新发布的商品 status=0（待审核），**只有审核通过才能被其他人看到** |
| BR-P07 | 只有**在售（status=1）**的商品能被购买 |
| BR-P08 | 只有**商品的所有者**能编辑/下架/删除自己的商品 |
| BR-P09 | 已被购买的订单关联的商品，**不允许删除**（外键约束） |
| BR-P10 | 浏览量在**打开详情页**时 +1（独立于业务查询，不能因为其他接口调用而虚增） |

### 6.2 订单规则

| 编号 | 规则 |
|------|------|
| BR-O01 | **不能购买自己发布的商品** |
| BR-O02 | 下单时商品必须 status=1（在售），否则报"已售出或已下架" |
| BR-O03 | **同一商品同时只能有一个 status=0（待交易）的订单** —— 防止多人重复预定 |
| BR-O04 | 订单创建后，双方**互相可见联系方式**（买家的"我买到的"看卖家手机号，卖家的"我卖出的"看买家手机号） |
| BR-O05 | **只有卖家**能确认交易完成（`complete`），确认时用**乐观锁**：`UPDATE product SET status=2 WHERE id=? AND status=1`，影响行数为 0 说明商品已非在售 |
| BR-O06 | 确认完成时，同一事务内：`order.status` 0→3，`product.status` 1→2，`order.finish_time`=now |
| BR-O07 | **买家**可取消自己 status=0 的订单（`cancel`） |
| BR-O08 | **卖家**也可拒绝 status=0 的订单（同样是取消，用于处理恶意下单） |
| BR-O09 | 只有 status=0 的订单能取消；已完成的订单不可取消 |
| BR-O10 | **平台不处理资金**，`pay_method` 只是线下付款方式的意向记录，不产生任何扣款 |
| BR-O11 | 订单取消后，商品状态**保持 status=1（仍在售）**，可被其他人继续购买 |

> ⚠️ **BR-O03 是本模型的关键约束**：因为平台不锁资金，如果允许多个待交易订单，卖家会被无数人同时联系。
> 实现方式：下单前查 `SELECT COUNT(*) FROM product_order WHERE product_id=? AND status=0`，>0 则拒绝。
> 并发下用**唯一索引**兜底：`UNIQUE KEY uk_product_pending (product_id, status)` 无法直接用（status 会变），
> 因此采用**应用层校验 + 事务**，并在文档中注明这是已知的权衡点。

### 6.3 联系方式与隐私

| 编号 | 规则 |
|------|------|
| BR-C01 | `user.phone` 作为**唯一的联系方式**（用户注册时选填，但**发布商品前必须填**） |
| BR-C02 | 手机号**不在商品列表/详情页公开**，只在两处暴露：**订单详情**（交易双方）、**卖家主页**（仅"联系卖家"按钮点击后展示） |
| BR-C03 | 未登录用户**不能查看任何联系方式** → `401` |
| BR-C04 | 没有进行中订单的用户，访问商品详情时**看不到卖家手机号**（防止爬取） |
| BR-C05 | 发布商品时若用户未填手机号 → `400 请先完善手机号，便于买家联系你` |

> 💡 **这是一处有意的取舍**：本项目为了让交易能落地，把手机号暴露给交易对方。
> 真实平台会用"平台内聊天"替代手机号交换 —— 那需要 WebSocket（本项目已砍）。
> 答辩时如果被问"隐私怎么办"，答：*"这是信息撮合模式的固有代价；正规做法是用站内信或虚拟号码中转，本项目因工期限制采用了直接交换，并在需求文档中明确标注了这一限制。"*

| 编号 | 规则 |

## 11. 非功能性需求

| 项 | 要求 |
|----|------|
| 安全 | 密码 BCrypt；JWT 鉴权；SQL 参数化（MyBatis-Plus / `?` 占位符） |

## 12. 对照参考项目的改进清单

> 这些是参考项目**真实存在的缺陷**，本项目逐一修正。答辩时可作为"我做了什么改进"的素材。

| # | 参考项目的缺陷 | 位置 | 本项目的做法 |
|:-:|----------------|------|--------------|
| 1 | 密码**明文**存储与比对 | `UserServiceImpl:65,110,116` | BCrypt 加密 |
| 2 | **未注册分页插件**，`selectPage` 静默失效 | 无 `MybatisPlusConfig` | 显式注册 `PaginationInnerInterceptor` |

## 14. 需求变更记录

| 版本 | 日期 | 变更内容 |
|------|------|----------|
| v1.0 | — | 需求冻结：完成 25 项设计决策，见 `PLAN.md` 决策记录 |
| **v1.1** | — | ⭐ **交易模型根本性变更**：由"平台内支付+资金托管+确认收货"改为**信息撮合模式**（平台不碰钱，交易线下完成）。连带影响：<br>① 订单状态由 4 态（0待付款/1已付款/3已完成/4已取消）简化为 **3 态（0待交易/3已完成/4已取消）**<br>② 确认完成的权限由"买家"改为 **"卖家"**<br>③ 删除 `/api/orders/{id}/pay` 接口（接口总数 39 → 38）<br>④ `product_order` 表删除 `pay_time` 字段，新增 `cancel_time`/`cancel_reason`<br>⑤ 新增 **BR-C（联系方式与隐私）** 规则组，明确 `phone` 字段的暴露范围<br>⑥ 新增页面 **P09 下单成功页**、**P10 订单详情页**<br>⑦ 新增业务约束 BR-O03：同一商品同时只能有一个待交易订单 |

### 变更原因说明

原设计照搬电商的"付款→托管→确认收货→打款"流程，但在本项目约束下（**不做钱包、不做聊天、不做评价、不做邮寄**）存在**无法自圆其说的逻辑漏洞**：

- 平台没有真实资金流，"退款"无从谈起
- 没有物流凭证和聊天记录，平台无法仲裁"到底交付了没有"
- 没有评价体系，双方履约意愿无任何约束

**新方案（信息撮合）彻底消除了这些分支**：平台从始至终不涉及金额，只负责"让买卖双方联系上"和"记录交易结果"。这既符合校园二手交易的真实场景，也让系统逻辑变得可证明的正确。
