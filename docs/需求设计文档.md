## 1. 业务背景与目标

### 1.1 项目定位

面向**高校校园**的二手商品交易平台。学生在平台上发布闲置物品，其他学生浏览、购买，**线下当面交易**（校内见面交付，不走物流）。

### 1.2 与原参考项目的本质区别

| 维度 | 参考项目（智循书堂） | 本项目 |
|------|---------------------|--------|
| 商品类型 | 只有教材（有 ISBN、作者、出版社） | **全品类二手商品**（数码/家电/服饰/运动…） |
| 库存模型 | 有多库存字段（但代码没实现扣减） | **纯单品制**：一件商品 = 一条记录 |
| 交易方式 | 邮寄（有收货地址） | **校园当面交易**（有交易地点） |
| 议价 | 无 | 无（一口价） |
| 支付 | 仅改状态 | 模拟支付（选支付宝/微信 + 支付动画） |
| 互动 | 几乎为零 | **收藏（想要）+ 行为埋点 + 卖家主页** |
| 前端 | 通用 Element Plus 蓝色风格 | **仿闲鱼黄色视觉**，自定义样式 |

> ⚠️ 因此**不能复用原项目的表结构**。本项目表结构从业务属性重新推导（见第 5 章）。

### 1.3 学习与交付目标

- **学习目标**：掌握 Spring Boot 分层架构、MyBatis-Plus、JWT 鉴权、Redis 缓存（后期）、AI 服务集成（后期）
- **交付物**：可运行系统 + 实验报告 + 答辩 PPT + 演示视频

## 3. 角色与权限

### 3.1 角色定义

**只有两种角色**（简化于闲鱼的"人人可买卖"模型）：

| 角色 | 说明 | 权限范围 |
|------|------|----------|
| **游客**（未登录） | 无账号访问者 | 浏览商品列表、商品详情、卖家主页、分类 |
| **user** | 注册用户，**既可买也可卖** | 游客权限 + 发布商品、下单、收藏、查看自己的订单与商品 |
| **admin** | 管理员 | 全部权限 + 审核商品、下架商品、管理用户、查看全量数据 |

> 🔑 **关键设计**：不区分"买家/卖家"角色。同一个 `user` 发布商品时是卖家、下单时是买家，**身份由行为决定**。
> 参考项目的 `role` 里有 `seller` 值，本项目**取消**。

### 3.2 权限矩阵

| 功能 | 游客 | user | admin |
|------|:----:|:----:|:-----:|
| 浏览商品列表/详情 | ✅ | ✅ | ✅ |
| 搜索/筛选/排序 | ✅ | ✅ | ✅ |
| 查看卖家主页 | ✅ | ✅ | ✅ |
| 注册/登录 | ✅ | — | — |
| 发布商品 | ❌ | ✅ | ✅ |
| 立即购买 | ❌ | ✅ | ✅ |
| 收藏/取消收藏 | ❌ | ✅ | ✅ |
| 我的订单/我发布的/我的收藏 | ❌ | ✅ | ✅ |
| 编辑/下架自己的商品 | ❌ | ✅ | ✅ |
| 商品审核/下架他人商品 | ❌ | ❌ | ✅ |
| 用户管理（禁用/启用） | ❌ | ❌ | ✅ |
| 数据统计 | ❌ | ❌ | ✅ |

### 3.3 鉴权实现

- **认证**：JWT。登录成功返回 token，前端存 `localStorage`，后续请求带 `Authorization: Bearer <token>`
- **拦截器**：`JwtInterceptor` 校验 token → 把 `userId/username/role` 放进 request attribute
- **上下文**：`UserContext.getCurrentUserId()` 供 Service 层取当前用户
- **管理员**：`AdminInterceptor` 校验 role 是否为 admin
- **密码**：BCrypt 加密存储（**修正参考项目的明文密码缺陷**）

## 4. 核心业务流程

### 4.1 商品生命周期

```
              [卖家发布]
                  ↓
   ┌─────────── status = 0 待审核 ───────────┐
   │                                          │
[管理员通过]                            [管理员拒绝]
   ↓                                          ↓
status = 1 在售                          status = 4 已拒绝
   │
   ├──────────────[卖家主动下架]──────────────→ status = 3 已下架
   │
   └──────────────[买家付款成功]──────────────→ status = 2 已售出
                                                     │
                                          [订单取消]──┴──→ 回到 status = 1 在售
```

**状态枚举**：

| 值 | 名称 | 说明 |
|:--:|------|------|
| 0 | 待审核 | 刚发布，仅自己和管理员可见 |
| 1 | 在售 | 已上架，所有人可见、可购买 |
| 2 | 已售出 | 有买家付款，不可再购买 |
| 3 | 已下架 | 卖家主动下架 |
| 4 | 已拒绝 | 管理员审核不通过 |

> 参考项目的 bug：「下架」接口把 status 写成了 2（与"已售出"混用）。本项目的 3 专门表示"已下架"。

### 4.2 订单生命周期

```
[买家点"立即购买"]
        ↓
  status = 0 待付款 ──────[买家取消]──────→ status = 4 已取消
        │                                        │
    [模拟支付成功]                        [商品恢复在售]
        ↓
  status = 1 已付款（等待线下交易）
        │
  [买家线下拿到商品，点"确认完成"]
        ↓
  status = 3 已完成
```

**状态枚举**：

| 值 | 名称 | 说明 |
|:--:|------|------|
| 0 | 待付款 | 订单已创建，商品被锁定 |
| 1 | 已付款 | 支付完成，等待线下交付 |
| 3 | 已完成 | 买家确认收到商品 |
| 4 | 已取消 | 订单作废，商品恢复在售 |

> **说明**：`2` 状态（已发货）在参考项目中存在，但本项目**不做邮寄**，因此**跳过 2**。
> 编号保持与参考项目一致（0/1/3/4），方便对照学习，但业务上不产生 2。

### 4.3 下单主流程（时序）

```
买家                   前端                后端                    数据库
 │                  商品详情页
 │──点"立即购买"────→ 结算页
 │                   （显示商品+交易地点）
 │──选支付方式──────→ POST /api/orders {productId}
 │                   ←──────────────────── OrderController.create()
 │                                         ├ 校验商品 status=1
 │                                         ├ 校验不是自己买自己
 │                                         └ INSERT order(status=0)
 │                   ←── 返回 orderId
 │──点"确认支付"────→ PUT /api/orders/{id}/pay
 │                   ←──────────────────── OrderController.pay()
 │                                         ├ 校验订单归属 + status=0
 │                                         ├ 乐观锁: UPDATE product SET status=2 WHERE id=? AND status=1
 │                                         ├ 若影响行数=0 → 报"已被买走"
 │                                         └ UPDATE order SET status=1
 │                   ←── "支付成功"
 │──线下见面拿到商品──→ PUT /api/orders/{id}/complete
 │                                         └ UPDATE order SET status=3
```

**并发安全**：付款时用**乐观锁**（`UPDATE ... WHERE status = 1` 判断影响行数）防止同一商品被两人同时买走。
> 参考项目的 `checkBookLock()` 只是重新查一次状态，**没有真正加锁**，存在超卖风险。

**删除的字段**：`isbn`（→`brand`）、`author`（教材专用）、`stock`（单品制无意义）、`trade_count`（已由 favorite_count + 订单数替代）。

> 💡 `favorite_count` 是**冗余字段**：收藏/取消收藏时同步维护。这样商品列表不用 JOIN 收藏表算数量，是典型的"用写入成本换查询性能"。

### 5.5 `product_order` 订单表

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| id | int | PK, AUTO | 订单ID |
| order_no | varchar(50) | NOT NULL, UNIQUE | 订单号（时间戳+UUID） |
| buyer_id | int | NOT NULL, FK→user.id | 买家ID |
| seller_id | int | NOT NULL, FK→user.id | 卖家ID（下单时快照） |
| product_id | int | NOT NULL, FK→product.id | 商品ID |
| product_title | varchar(100) | NOT NULL | **商品标题快照**（商品被删也不影响订单） |
| product_image | varchar(255) | | **商品主图快照** | 
| price | decimal(10,2) | NOT NULL | 成交价（下单时快照） |
| status | tinyint | DEFAULT 0 | 0待付款/1已付款/3已完成/4已取消 |
| pay_method | varchar(20) | | 支付方式：alipay / wechat |
| trade_place | varchar(100) | | **交易地点快照**（替代收货地址） |
| buyer_remark | varchar(255) | | 买家备注 |
| pay_time | datetime | | 付款时间 |
| finish_time | datetime | | 完成时间 |
| create_time | datetime | DEFAULT now | 下单时间 |

**删除的字段**：`address_name`、`address_phone`、`address_detail`（不做邮寄）。

> 💡 **快照设计**：`product_title`/`price`/`trade_place` 存的是**下单瞬间的副本**。这样即使卖家改了价格或删了商品，历史订单依然显示当时的真实信息 —— 这是电商订单的标准做法。

### 5.6 `favorite` 收藏表（新增）

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| id | int | PK, AUTO | |

| create_time | datetime | DEFAULT now | 收藏时间 |

### 5.7 `user_behavior` 行为表

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| id | int | PK, AUTO | |
| user_id | int | NOT NULL | 用户ID |
| product_id | int | NOT NULL | 商品ID |
| behavior_type | tinyint | NOT NULL | **1=浏览 / 2=收藏 / 3=购买** |
| behavior_time | datetime | DEFAULT now | 行为时间 |

**索引**：`(user_id)`、`(product_id)`、`(behavior_type)`

## 6. 业务规则

### 6.1 商品规则

| 编号 | 规则 |
|------|------|
| BR-P01 | 商品标题 5~100 字符，必填 |
| BR-P02 | 价格必须 > 0，最多两位小数 |
| BR-P03 | 原价可选；若填写，必须 ≥ 现价 |
| BR-P04 | 图片最多 9 张，格式 JPG/PNG/GIF/WebP，单张 ≤ 5MB |
| BR-P05 | 成色取值限定：`全新` / `几乎全新` / `轻微使用痕迹` / `明显使用痕迹` |
| BR-P06 | 新发布的商品 status=0（待审核），**只有审核通过才能被其他人看到** |
| BR-P07 | 只有**在售（status=1）**的商品能被购买 |
| BR-P08 | 只有**商品的所有者**能编辑/下架/删除自己的商品 |
| BR-P09 | 已被购买的订单关联的商品，**不允许删除**（外键约束） |
| BR-P10 | 浏览量在**打开详情页**时 +1（独立于业务查询，不能因为其他接口调用而虚增） |

### 6.2 订单规则

| 编号 | 规则 |
|------|------|
| BR-O01 | **不能购买自己发布的商品** |
| BR-O02 | 下单时商品必须 status=1，否则报"已售出/已下架" |
| BR-O03 | 付款时用**乐观锁**校验：`UPDATE product SET status=2 WHERE id=? AND status=1`，影响行数为 0 说明被别人抢先买走 |
| BR-O04 | 只有**买家本人**能支付/取消/确认完成自己的订单 |
| BR-O05 | 只有**待付款(0)** 的订单能支付或取消 |
| BR-O06 | 只有**已付款(1)** 的订单能确认完成 |
| BR-O07 | 取消订单时，商品状态从 2 恢复为 1（重新上架） |
| BR-O08 | 订单一旦创建，商品立即被"锁定"（status 由 1→2 在**付款时**执行，创建时仅创建订单） |

> ⚠️ **BR-O03 和 BR-O08 的配合**：本项目采用"下单不算锁定，**付款才算锁定**"的策略。
> 好处：避免恶意用户下单不付款把商品锁死。
> 代价：可能出现两人同时创建订单，后付款者失败（会被乐观锁挡下并提示）。

### 6.3 收藏规则

| 编号 | 规则 |
|------|------|
| BR-F01 | 同一用户对同一商品只能收藏一次（唯一约束） |
| BR-F02 | 收藏时 `product.favorite_count` +1，取消时 -1 |
| BR-F03 | 不能收藏自己发布的商品 |
| BR-F04 | 收藏行为写入 `user_behavior`（type=2） |

### 6.4 用户规则

| 编号 | 规则 |
|------|------|
| BR-U01 | 用户名唯一，4~20 字符 |
| BR-U02 | 密码 6~20 字符，**BCrypt 加密存储，严禁明文** |
| BR-U03 | 手机号选填，若填写需匹配 `^1[3-9]\d{9}$` |
| BR-U04 | status=0 的账号不允许登录 |
| BR-U05 | 管理员不能禁用自己 |

### 6.5 行为埋点规则

| 编号 | 规则 |
|------|------|
| BR-B01 | 只有**已登录**用户的行为才记录（游客不记） |
| BR-B02 | **不记录自己对自己商品**的行为 |
| BR-B03 | 浏览记录：打开商品详情页时写入 |
| BR-B04 | 收藏记录：收藏时写入 |
| BR-B05 | 购买记录：付款成功时写入 |
| BR-B06 | 同一行为可重复记录（日志表语义，不去重） |

## 10. 技术架构

### 10.1 部署拓扑（端口分配）

| 服务 | 端口 | 说明 |
|------|:----:|------|
| MySQL | 3306 | 共用系统实例，库名 `secondhand_shop` |

| （后期）FastAPI AI 服务 | **8001** | 避开参考项目的 8000 |
| （后期）Redis | 6379 | |

### 10.2 后端分层

```
Controller  接收请求、参数校验、返回 Result<T>
    ↓
Service     业务逻辑（事务边界在这里）
    ↓
Mapper      MyBatis-Plus 数据访问
    ↓
MySQL
```

**统一响应格式**：

```json
{
  "code": 200,
  "message": "success",
  "data": { }
}
```

| code | 含义 |
|:----:|------|
| 200 | 成功 |
| 400 | 参数错误 / 业务校验失败 |
| 401 | 未登录 / token 失效 |
| 403 | 无权限（非管理员、非本人） |
| 404 | 资源不存在 |
| 500 | 服务器内部错误 |

### 10.3 前端架构

```
views/          页面
components/     可复用组件（商品卡片、导航栏、分页…）
api/            接口封装（按模块拆分）
router/         路由 + 守卫（requiresAuth / requiresAdmin）
utils/request.js   Axios 实例 + 拦截器
styles/         全局样式 + CSS 变量（色板）
```

## 11. 非功能性需求

| 项 | 要求 |
|----|------|
| 安全 | 密码 BCrypt；JWT 鉴权；SQL 参数化（MyBatis-Plus / `?` 占位符） |
| 性能 | 商品列表分页（**必须注册 MyBatis-Plus 分页插件**，否则静默失效）；列表页 N+1 查询要消除 |
| 并发 | 付款用乐观锁防超卖 |
| 健壮 | 全局异常处理，不向前端泄漏堆栈 |
| 数据一致性 | 下单/付款/取消用 `@Transactional`；事务加在 Service 层 |
| 可维护 | 状态码用**枚举**而非魔法数字；不硬编码分类 ID |

## 12. 对照参考项目的改进清单

> 这些是参考项目**真实存在的缺陷**，本项目逐一修正。答辩时可作为"我做了什么改进"的素材。

| # | 参考项目的缺陷 | 位置 | 本项目的做法 |
|:-:|----------------|------|--------------|
| 1 | 密码**明文**存储与比对 | `UserServiceImpl:65,110,116` | BCrypt 加密 |
| 2 | **未注册分页插件**，`selectPage` 静默失效 | 无 `MybatisPlusConfig` | 显式注册 `PaginationInnerInterceptor` |
| 3 | 详情接口在 GET 里**写库**（浏览+1），且无 null 判断会 NPE | `BookServiceImpl:32-38` | 浏览量独立处理，加 null 防护 |
| 4 | 购物车**N+1 查询** + 虚增浏览量 | `CartController:35-45` | 无购物车；批量查询 |
| 5 | **分类 ID 硬编码且错误**（156/164 实际是子分类） | `BookPublish.vue:29,37` | 从接口动态获取 |
| 6 | 下单**没有真正加锁**，注释自承可用 Redis | `OrderController:358-362` | 乐观锁 `UPDATE ... WHERE status=1` |
| 7 | 状态码**魔法数字**散落各处 | 全项目 | 枚举 `ProductStatus` / `OrderStatus` |
| 8 | `deleted` 逻辑删除**配置无效**（表无该列） | `application.yml:30-32` | 要么真加列，要么删掉该配置 |
| 9 | 异常被吞 + 细节外泄 | `CartController`、`UploadController` | 统一全局异常处理 |
| 10 | `user_behavior` 表**建了却从未写入** | 全项目 | 补上三类埋点 |
| 11 | 「下架」与「已售出」**混用 status=2** | `BookController:158` | 新增 status=3 表示已下架 |
| 12 | 明文密码 + `@Transactional` 加在 Controller 层 | `OrderController:39` | 事务放在 Service 层 |
