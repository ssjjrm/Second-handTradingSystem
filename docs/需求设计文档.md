## 1. 业务背景与目标

### 1.1 项目定位

面向**高校校园**的二手商品交易平台。学生在平台上发布闲置物品，其他学生浏览、购买，**线下当面交易**（校内见面交付，不走物流）。

### 1.2 与原参考项目的本质区别

| 维度 | 参考项目（智循书堂） | 本项目 |
|------|---------------------|--------|
| 商品类型 | 只有教材（有 ISBN、作者、出版社） | **全品类二手商品**（数码/家电/服饰/运动…） |
| 库存模型 | 有多库存字段（但代码没实现扣减） | **纯单品制**：一件商品 = 一条记录 |
| 交易方式 | 邮寄（有收货地址） | **校园当面交易**（有交易地点） |
| 议价 | 无 | 无（一口价） |
| 交易达成 | 平台内下单+支付+发货 | **信息撮合**：平台只促成联系，交易线下完成 |
| 互动 | 几乎为零 | **收藏（想要）+ 行为埋点 + 卖家主页** |
| 前端 | 通用 Element Plus 蓝色风格 | **仿闲鱼黄色视觉**，自定义样式 |

> ⚠️ 因此**不能复用原项目的表结构**。本项目表结构从业务属性重新推导（见第 5 章）。

### 1.3 学习与交付目标

- **学习目标**：掌握 Spring Boot 分层架构、MyBatis-Plus、JWT 鉴权、Redis 缓存（后期）、AI 服务集成（后期）
- **交付物**：可运行系统 + 实验报告 + 答辩 PPT + 演示视频

## 3. 角色与权限

### 3.1 角色定义

**只有两种角色**（简化于闲鱼的"人人可买卖"模型）：

| 角色 | 说明 | 权限范围 |
|------|------|----------|
| **游客**（未登录） | 无账号访问者 | 浏览商品列表、商品详情、卖家主页、分类 |
| **user** | 注册用户，**既可买也可卖** | 游客权限 + 发布商品、联系卖家、收藏、查看自己的商品与收藏 |
| **admin** | 管理员 | 全部权限 + 审核商品、下架商品、管理用户、查看全量数据 |

> 🔑 **关键设计**：不区分"买家/卖家"角色。同一个 `user` 发布商品时是卖家、联系别人时是买家，**身份由行为决定**。
> 参考项目的 `role` 里有 `seller` 值，本项目**取消**。

### 3.2 权限矩阵

| 功能 | 游客 | user | admin |
|------|:----:|:----:|:-----:|
| 浏览商品列表/详情 | ✅ | ✅ | ✅ |
| 搜索/筛选/排序 | ✅ | ✅ | ✅ |
| 查看卖家主页 | ✅ | ✅ | ✅ |
| 注册/登录 | ✅ | — | — |
| 发布商品 | ❌ | ✅ | ✅ |
| 联系卖家（看联系方式） | ❌ | ✅ | ✅ |
| 收藏/取消收藏 | ❌ | ✅ | ✅ |
| 我发布的/我的收藏/联系方式设置 | ❌ | ✅ | ✅ |
| **标为已售出**（仅自己的商品） | ❌ | ✅ | ✅ |
| 编辑/下架/删除自己的商品 | ❌ | ✅ | ✅ |
| 商品审核/下架他人商品 | ❌ | ❌ | ✅ |
| 用户管理（禁用/启用） | ❌ | ❌ | ✅ |
| 咨询记录 / 数据统计 | ❌ | ❌ | ✅ |

### 3.3 鉴权实现

- **认证**：JWT。登录成功返回 token，前端存 `localStorage`，后续请求带 `Authorization: Bearer <token>`
- **拦截器**：`JwtInterceptor` 校验 token → 把 `userId/username/role` 放进 request attribute
- **上下文**：`UserContext.getCurrentUserId()` 供 Service 层取当前用户
- **管理员**：`AdminInterceptor` 校验 role 是否为 admin
- **密码**：BCrypt 加密存储（**修正参考项目的明文密码缺陷**）

## 4. 核心业务流程

### 4.1 商品生命周期

```
              [卖家发布]
                  ↓
   ┌─────────── status = 0 待审核 ───────────┐
   │                                          │
[管理员通过]                            [管理员拒绝]
   ↓                                          ↓
status = 1 在售                          status = 4 已拒绝
   │
   ├──────────────[卖家主动下架]──────────────→ status = 3 已下架
   │
   └──────────[卖家确认交易完成]──────────────→ status = 2 已售出
```

**状态枚举**：

| 值 | 名称 | 说明 |
|:--:|------|------|
| 0 | 待审核 | 刚发布，仅自己和管理员可见 |
| 1 | 在售 | 已上架，所有人可见、可预定 |
| 2 | 已售出 | **卖家确认交易完成**后置为此状态，不可再预定 |
| 3 | 已下架 | 卖家主动下架 |
| 4 | 已拒绝 | 管理员审核不通过 |

> 参考项目的 bug：「下架」接口把 status 写成了 2（与"已售出"混用）。本项目的 3 专门表示"已下架"。

### 4.2 交易模型：**纯信息撮合，平台零参与交易** ⭐

这是本项目**最重要的设计决策**，经历了三次迭代才定下来。完整记录在这里，因为**它是答辩时最能体现思考深度的部分**。

#### 4.2.1 方案演进（三次否决）

**第一版设想：照搬电商的"平台担保"**
付款 → 平台托管 → 确认收货 → 打款卖家。

❌ **否决原因**：在"不做钱包/不做聊天/不做评价/不做邮寄"的约束下站不住脚：
- 平台没有真实资金流 —— "已付款"只是改了个状态位，**"退款"无从谈起**（从没扣过钱）
- 无交付凭证（没物流单号、没聊天记录）—— 平台**无法仲裁"到底交付了没有"**
- 无信任机制 —— 没有评价体系，履约意愿无任何约束

**第二版设想：订单=预定记录，卖家确认完成**
买家下单 → 双方看联系方式 → 线下交易 → **卖家点"确认已交易"** → 商品变已售出。

❌ **否决原因**（这个漏洞很隐蔽，但致命）：
> 卖家在线下用微信同时聊了 3 个买家，回到平台看到 3 条待交易订单 ——
> **他怎么知道刚刚成交的是哪一条？**
>
> 微信昵称和平台昵称大概率不一样，订单号更不可能在线下聊天时报出来。
> **"卖家选一个"这个动作在现实中无法可靠执行。**
> 一旦选错，真正成交的买家的订单没被完成，而没交易的人却显示已成交。

**第三版（最终）：纯信息撮合，没有订单**
平台只做一件事 —— **让买卖双方联系上**。交易本身完全在线下进行。

#### 4.2.2 最终方案

```
┌──────────────────────────────────────────────────────────┐
│  平台负责（系统内）          │  用户自己负责（线下）        │
├──────────────────────────────┼───────────────────────────┤
│  · 商品展示与搜索            │  · 加微信/QQ 沟通            │
│  · 展示卖家联系方式          │  · 见面交付商品             │
│  · 记录"谁想要过"（行为日志） │  · 当面付钱（现金/微信转账） │
│  · 卖家手动标记"已售出"      │  · 验货、议价（线下自行商量）│
│                              │  · 任何纠纷自行协商         │
└──────────────────────────────┴───────────────────────────┘
```

**平台从始至终：不产生订单、不涉及金额、不托管资金、不提供退款、不仲裁纠纷。**

#### 4.2.3 完整流程

```
【买家侧】
浏览器看中商品 → 点「联系卖家」
    ↓
  ┌─ 未登录 → 跳登录页
  └─ 已登录 → 弹出联系方式卡片
              ├─ 卖家微信号 / QQ号（可一键复制）
              └─ 交易地点
    ↓
  同时写入 user_behavior（type=4 咨询）→ 卖家能知道"有人想要"
    ↓
  自己加微信/QQ，线下约时间地点，面对面交易
    ↓
【卖家侧】
在「我发布的」里看到该商品「N 人想要」
    ↓
  线下成交后，手动点「标为已售出」
    ↓
  ┌─ 乐观锁：UPDATE product SET status=2 WHERE id=? AND status=1
  └─ 商品变已售出，不可再被联系
```

#### 4.2.4 这样设计的收益

| 收益 | 说明 |
|------|------|
| **零无法自圆其说的分支** | 没有"退不退款""谁确认""选错人"这类问题，因为**平台不参与交易过程** |
| **完全贴合校园真实场景** | 同学之间卖东西就是"闲鱼看到 → 加微信 → 食堂见面 → 微信转账" |
| **少一张表、少一套状态机** | 删掉 `product_order` 表，删掉订单状态机，删掉订单管理后台 |
| **"谁想要过"用行为日志实现** | 复用已有的 `user_behavior` 表（type=4），**不需要新建表** |
| **保留唯一的并发点** | 卖家标记售出时用乐观锁，防止"一件商品被同时标记两次" |

#### 4.2.5 代价（必须诚实记录）

| 代价 | 影响 | 缓解 |
|------|------|------|
| 没有订单数据 | 后台"数据统计"少了订单维度；个人中心少了"我买到的/我卖出的" | 统计改为：用户数 / 商品数 / 成交量（按已售出商品计）/ 咨询次数 |
| **无法追踪交易是否真的发生** | 卖家可能忘记标记已售出，商品一直挂着 | 「我发布的」列表对 N 人想要的商品加**醒目提醒** |
| 联系方式直接暴露 | 隐私问题；理论上可被爬取 | 见 §6.3 联系方式与隐私规则 |
| 无纠纷处理能力 | 被骗无法维权 | 校园场景 + 面交（可当场验货）风险较低；本文档明确标注此限制 |

> 💡 **答辩时如果被问"为什么不做订单系统"**，标准回答：
> *"我最初设计了订单系统，但推演后发现一个致命问题：卖家在线下和多个买家沟通后，回到平台无法可靠地辨认出哪一条订单对应刚成交的那个人——因为线下沟通（微信）和平台身份（昵称）无法对应。与其做一个会被误操作的系统，不如把平台定位为信息撮合，让交易在线下完成。这也正是校园二手交易的真实形态。"*

### 4.3 关键交互时序

```
买家                 前端                 后端                   数据库
 │               商品详情页
 │──点「联系卖家」─→
 │                ←────────────── ProductController.getContact(id)
 │                                ├ 未登录 → 401
 │                                └ 返回卖家联系方式 + 交易地点
 │                ←── { wechat, qq, tradePlace }
 │
 │                【联系方式弹窗】显示微信号/QQ（可复制）
 │                ──────────────→ POST /api/behaviors/contact
 │                                └ INSERT user_behavior(type=4)
 │
 │──自行加微信/QQ，线下见面交易（平台不参与）──────────────→
 │
卖家                 前端                 后端
 │                「我发布的」看到「2 人想要」
 │──线下成交─────→
 │──点「标为已售出」→
 │                ←────────────── ProductController.markSold(id)
 │                                ├ 校验是商品所有者
 │                                └ 乐观锁: UPDATE product SET status=2
 │                                          WHERE id=? AND status=1
 │                                └ 影响行数 0 → 400 商品已非在售状态
 │                ←── "已标记为售出"
```

**并发安全**：*这是本项目唯一的并发点*。用乐观锁（`UPDATE ... WHERE status=1` 判断影响行数）防止一件商品被重复标记。
> 参考项目的 `checkBookLock()` 只是重新查一次状态，**没有真正加锁**。
>
> 说实话：在这个模型下并发风险**本身就很低**（卖家自己点按钮，很难真的同时点两次）。保留乐观锁的价值在于**它是正确的写法**，且答辩时可以讲清楚"为什么这里要用它"以及"为什么实际风险低"。

## 5. 数据模型

### 5.1 表总览（**最终 5 张表**）

| 表名 | 说明 | 相对参考项目 |
|------|------|--------------|
| `user` | 用户 | 保留（去掉 `seller` 角色与 `balance`，密码改 BCrypt，**新增微信号/QQ 字段**） |
| `category` | 商品分类（两级） | 保留结构，**数据全部重设** |
| `product` | 商品 | **替代 `book`，字段重新设计** |
| `favorite` | **收藏（想要）** | **新增** —— 业务数据，用户可见可管理 |
| `user_behavior` | 用户行为日志 | 保留结构，**补上写入逻辑**，行为类型加 `4=咨询` |
| ~~`product_order`~~ | 订单 | **删除**（改为纯信息撮合，平台不产生订单） |
| ~~`cart`~~ | 购物车 | **删除**（不做购物车） |
| ~~`address`~~ | 收货地址 | **删除**（校园当面交易，用商品上的"交易地点"） |

> 🔑 **`favorite` 与 `user_behavior` 的区别**（两者都保留，职责不同）：
>
> | 表 | 性质 | 用户可见 | 约束 |
> |----|------|:--------:|------|
> | `favorite` | **业务数据** —— 用户主动收藏，在「我的收藏」里能看、能取消 | ✅ 有界面 | `UNIQUE(user_id, product_id)` 防重复 |
> | `user_behavior` | **日志流水** —— 浏览/收藏/咨询的记录，用于统计与后期 AI 推荐 | ❌ 无界面 | 可重复记录，不去重 |
>
> 两者**不是冗余**：删掉收藏后 `user_behavior` 里只剩一条无法取消的历史痕迹，用户无法回溯自己收藏了什么。

### 5.2 `user` 用户表

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| id | int | PK, AUTO | 用户ID |
| username | varchar(50) | NOT NULL, UNIQUE | 登录名 |
| password | varchar(100) | NOT NULL | **BCrypt 密文**（60 字符） |
| nickname | varchar(50) | | 昵称，默认取 username |
| **wechat** | varchar(50) | | **微信号**（联系方式，选填但发布商品前必须至少填一个） |
| **qq** | varchar(20) | | **QQ 号**（联系方式，同上） |
| phone | varchar(20) | | 手机号（选填，**不对外展示**，仅账号找回用） |
| avatar | varchar(255) | | 头像 URL |
| role | varchar(20) | DEFAULT 'user' | **只有 `user` / `admin`** |
| status | tinyint | DEFAULT 1 | 1=正常，0=禁用 |
| create_time | datetime | DEFAULT now | 注册时间 |

> **变更**：
> - **删除 `balance` 字段** —— 不做钱包
> - **取消 `seller` 角色值** —— 人人可买可卖
> - **新增 `wechat` / `qq`** —— 校园场景下学生之间基本不用电话，微信/QQ 才是真实联系方式
> - `password` 长度 100 足够放 BCrypt（60 字符）
> - `phone` 降级为**仅账号找回**用，不对外展示

**两级结构**：一级分类（9 个）+ 二级分类（每个一级下 4~6 个）。

### 5.4 `product` 商品表（核心）

| 字段 | 类型 | 约束 | 说明 | 来源 |
|------|------|------|------|------|
| id | int | PK, AUTO | 商品ID | |
| title | varchar(100) | NOT NULL | 商品标题 | 参考 title |
| description | text | | 详细描述 | 参考 description |
| category_id | int | | 分类ID | 参考 category_id |
| condition_level | varchar(20) | | **成色**：全新/几乎全新/轻微使用痕迹/明显使用痕迹 | 参考 condition_level（**本轮才开始真正使用**） |
| price | decimal(10,2) | NOT NULL | 现价 | 参考 price |
| original_price | decimal(10,2) | | 原价（用于展示"省了多少"） | 参考 original_price |
| images | text | | **图片URL列表，JSON 数组字符串** | 参考 images（结构升级） |
| brand | varchar(50) | | 品牌/型号 | **替代 `isbn`** |
| trade_place | varchar(100) | | **交易地点**（如"东区食堂门口"） | **新增** |
| seller_id | int | NOT NULL, FK→user.id | 卖家ID | 参考 seller_id |
| status | tinyint | DEFAULT 0 | 0待审/1在售/2已售出/3已下架/4已拒绝 | 参考 status（**新增 3**） |
| view_count | int | DEFAULT 0 | 浏览量 | 参考 view_count |

**删除的字段**：`isbn`（→`brand`）、`author`（教材专用）、`stock`（单品制无意义）、`trade_count`（"想要数"改由 `favorite_count` 承担）。

> 💡 `favorite_count` 是**冗余字段**：收藏/取消收藏时同步维护。这样商品列表不用 JOIN 收藏表算数量，是典型的"用写入成本换查询性能"。

### 5.5 `favorite` 收藏表（想要）

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| id | int | PK, AUTO | |
| user_id | int | NOT NULL, FK→user.id | 收藏人 |
| product_id | int | NOT NULL, FK→product.id | 被收藏商品 |
| create_time | datetime | DEFAULT now | 收藏时间 |

**唯一约束**：`UNIQUE KEY uk_user_product (user_id, product_id)` —— 防止重复收藏。

**索引**：`(user_id, create_time DESC)` —— 支撑"我的收藏"按时间倒序分页。

> 💡 **这是业务表，不是日志表**：
> - 用户能在「我的收藏」里看到自己收藏了什么，能取消收藏
> - 唯一约束保证同一商品只收藏一次
> - `product.favorite_count`（冗余计数）就是这张表的聚合结果，收藏/取消时同步维护

### 5.6 `user_behavior` 行为日志表

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| id | int | PK, AUTO | |
| user_id | int | NOT NULL, FK→user.id | 用户ID |
| product_id | int | NOT NULL, FK→product.id | 商品ID |
| behavior_type | tinyint | NOT NULL | **1=浏览 / 2=收藏 / 3=咨询 / 4=取消收藏** |
| behavior_time | datetime | DEFAULT now | 行为时间 |

**索引**：`(user_id, behavior_time)`、`(product_id)`、`(behavior_type)`

**行为类型说明**：

| 值 | 类型 | 触发时机 | 用途 |
|:--:|------|----------|------|
| 1 | 浏览 | 打开商品详情页 | AI 推荐主信号 |
| 2 | 收藏 | 点「想要」 | AI 推荐强信号 |
| 3 | **咨询** | 点「联系卖家」查看联系方式 | **卖家看"谁想要过"的唯一数据源** |
| 4 | 取消收藏 | 取消「想要」 | 负反馈信号 |

> ⚠️ **这是日志表**：同一商品浏览 3 次就有 3 条记录，**不去重**。推荐计算时按 `(user_id, product_id)` 聚合。
>
> 🔑 **`behavior_type=3（咨询）` 在本项目有特殊作用**：因为平台不产生订单，**它是卖家"知道有人想要"的唯一途径**。
> 卖家在「我发布的」列表里看到的「N 人想要」= 对该商品 behavior_type=3 的**去重用户数**（`COUNT(DISTINCT user_id)`）。
>
> 参考项目建了这张表却**从未写入**（0 条数据），本项目补上完整埋点。

### 5.7 ER 关系

```
                  ┌──────────┐
                  │  user    │
                  └────┬─────┘
                       │ 1
          ┌────────────┼────────────┐
          │ N          │ N          │ N
     ┌────▼─────┐ ┌────▼─────┐ ┌────▼──────────┐
     │ product  │ │ favorite │ │ user_behavior │
     └────┬─────┘ └──────────┘ └───────────────┘
          │ 1            ▲ N          ▲ N
          │              │            │
          └──────────────┴────────────┘
        (favorite.product_id 与
         user_behavior.product_id 都指向 product.id)

     ┌──────────┐
     │ category │◄──┐  自关联：parent_id → category.id
     └────┬─────┘   │
          │ 1       │
          │ N       │
     ┌────▼─────┐   │
     │ product  │───┘ (category_id → category.id)
     └──────────┘
```

**外键汇总**：

| 表 | 外键 | 指向 | 删除策略 |
|----|------|------|----------|

| `favorite` | `product_id` | `product.id` | CASCADE（商品删除时收藏记录一并清除） |
| `user_behavior` | `user_id` | `user.id` | CASCADE |
| `user_behavior` | `product_id` | `product.id` | CASCADE |

## 6. 业务规则

### 6.1 商品规则

| 编号 | 规则 |
|------|------|
| BR-P01 | 商品标题 5~100 字符，必填 |
| BR-P02 | 价格必须 > 0，最多两位小数 |
| BR-P03 | 原价可选；若填写，必须 ≥ 现价 |
| BR-P04 | 图片最多 9 张，格式 JPG/PNG/GIF/WebP，单张 ≤ 5MB |
| BR-P05 | 成色取值限定：`全新` / `几乎全新` / `轻微使用痕迹` / `明显使用痕迹` |
| BR-P06 | 新发布的商品 status=0（待审核），**只有审核通过才能被其他人看到** |
| BR-P07 | 只有**在售（status=1）**的商品能被联系（"联系卖家"按钮仅对在售商品可用） |
| BR-P08 | 只有**商品的所有者**能编辑/下架/删除自己的商品 |
| BR-P09 | 只有**商品的所有者**能把商品标为"已售出" |
| BR-P10 | 浏览量在**打开详情页**时 +1（独立于业务查询，不能因为其他接口调用而虚增） |
| BR-P11 | 商品删除时，其关联的 `favorite` 与 `user_behavior` 记录**级联删除**（外键 CASCADE） |

### 6.2 交易与售出规则

> 本项目**没有订单**。交易在线下完成，平台只记录"谁咨询过"和"商品是否已售出"。

| 编号 | 规则 |
|------|------|
| BR-T01 | 买家点「联系卖家」后，**必须已登录**，否则跳登录页 |
| BR-T02 | **不能联系自己发布的商品**（自己不显示"联系卖家"按钮） |
| BR-T03 | 查看联系方式时写入 `user_behavior`（type=3 咨询），**同一用户对同一商品多次查看会记录多条**（日志语义） |
| BR-T04 | 卖家点「标为已售出」时用**乐观锁**：`UPDATE product SET status=2 WHERE id=? AND status=1`，影响行数为 0 → `400 商品已非在售状态`（防止重复标记） |
| BR-T05 | 只有 **status=1（在售）** 的商品能标为已售出 |
| BR-T06 | 标为已售后，商品**不能改回在售**（如需重新出售，由卖家重新发布） |
| BR-T07 | **平台不产生订单、不计算金额、不托管资金、不提供退款** |
| BR-T08 | 「我发布的」列表中，"N 人想要" = 对该商品 type=3 行为的**去重用户数**（`COUNT(DISTINCT user_id)`） |
| BR-T09 | 有咨询记录（N>0）的**在售**商品，在「我发布的」里显示**醒目提醒**（"有 N 人想要，成交后请及时标记售出"），降低遗忘率 |

### 6.3 联系方式与隐私

买家要看卖家的微信/QQ 才能联系 —— 这是本模型能成立的**硬前提**。

| 编号 | 规则 |
|------|------|
| BR-C01 | `user.wechat` / `user.qq` 是**交易联系方式**；注册时选填，但**发布商品前必须至少填一个** |
| BR-C02 | 联系方式**不在商品列表/详情页直接展示**，必须点「联系卖家」按钮才弹出（降低被批量爬取的成本） |
| BR-C03 | 未登录用户**不能查看任何联系方式** → `401 请先登录后再联系卖家` |
| BR-C04 | 只能查看**在售（status=1）**商品的卖家联系方式；已售出/已下架 → `400 该商品已不可交易` |
| BR-C05 | 未填联系方式的用户尝试发布商品 → `400 请先完善微信号或QQ号，便于买家联系你` |
| BR-C06 | `phone` 手机号字段**不对外展示**，仅用于账号找回 |
| BR-C07 | 卖家主页展示联系方式的方式与商品详情页一致（需登录 + 点按钮） |

> 💡 **这是一处有意的取舍，必须记录**：
>
> 平台为了让交易能落地，把联系方式暴露给潜在买家。真实平台会用"站内聊天"替代联系方式交换 —— 那需要 WebSocket（本项目已砍，见 §2.4）。
>
> **答辩时如果被问"隐私怎么办"**，标准回答：
> *"这是信息撮合模式的固有代价。正规做法有两种：一是站内聊天，二是虚拟号码中转（如闲鱼的'号码保护'）。本项目因工期限制采用直接交换联系方式，但在设计上做了两层收敛：联系方式不随列表返回、必须登录并主动点击才能查看，以此提高批量爬取的成本。这一点已在需求文档 §6.3 中明确标注为已知限制。"*

### 6.4 收藏（想要）规则

| 编号 | 规则 |
|------|------|
| BR-F01 | 同一用户对同一商品只能收藏一次（`UNIQUE(user_id, product_id)` 兜底） |
| BR-F02 | 收藏时 `product.favorite_count` +1，取消时 -1（**不低于 0**） |
| BR-F03 | 不能收藏自己发布的商品 |
| BR-F04 | 收藏写入 `favorite` 表（业务数据），**同时**写入 `user_behavior`（type=2，日志） |
| BR-F05 | 取消收藏时删除 `favorite` 记录，**同时**写入 `user_behavior`（type=4，负反馈） |
| BR-F06 | 重复收藏**幂等成功**（不报错，也不重复 +1） |
| BR-F07 | 「我的收藏」**包含已售出/已下架的商品**，前端显示灰色蒙层 + "已售出"标识，用户可手动移除 |
| BR-F08 | 商品被删除时，收藏记录级联删除 |

### 6.5 用户规则

| 编号 | 规则 |
|------|------|
| BR-U01 | 用户名唯一，4~20 字符 |
| BR-U02 | 密码 6~20 字符，**BCrypt 加密存储，严禁明文** |
| BR-U03 | 手机号选填，若填写需匹配 `^1[3-9]\d{9}$` |
| BR-U04 | 微信号 ≤50 字符；QQ 号选填，若填写需匹配 `^[1-9]\d{4,11}$` |
| BR-U05 | status=0 的账号不允许登录 |
| BR-U06 | 管理员不能禁用自己 |
| BR-U07 | 任何 user 角色**既可发布商品也可联系卖家**（不区分买家/卖家） |

### 6.6 行为埋点规则

| 编号 | 规则 |
|------|------|
| BR-B01 | 只有**已登录**用户的行为才记录（游客不记） |
| BR-B02 | **不记录"浏览自己商品"**的行为（无意义噪声）；但"咨询/收藏自己商品"本就被禁止 |
| BR-B03 | **浏览**：打开商品详情页时写入（type=1） |
| BR-B04 | **收藏**：收藏成功时写入（type=2） |
| BR-B05 | **咨询**：查看卖家联系方式时写入（type=3）—— **卖家"谁想要过"的唯一数据源** |
| BR-B06 | **取消收藏**：取消成功时写入（type=4）—— 负反馈信号 |
| BR-B07 | 同一行为**可重复记录**（日志表语义，不去重），推荐计算时按 `(user_id, product_id)` 聚合 |
| BR-B08 | 埋点失败**不能影响主业务流程**（如浏览记录写失败，不能导致详情页打不开） |

### 10.2 后端分层

```
Controller  接收请求、参数校验、返回 Result<T>
    ↓
Service     业务逻辑（事务边界在这里）
    ↓
Mapper      MyBatis-Plus 数据访问
    ↓
MySQL
```

**统一响应格式**：

```json
{
  "code": 200,
  "message": "success",
  "data": { }
}
```

| code | 含义 |
|:----:|------|
| 200 | 成功 |
| 400 | 参数错误 / 业务校验失败 |
| 401 | 未登录 / token 失效 |
| 403 | 无权限（非管理员、非本人） |
| 404 | 资源不存在 |
| 500 | 服务器内部错误 |

### 10.3 前端架构

```
views/          页面
components/     可复用组件（商品卡片、导航栏、分页…）
api/            接口封装（按模块拆分）
router/         路由 + 守卫（requiresAuth / requiresAdmin）
utils/request.js   Axios 实例 + 拦截器
styles/         全局样式 + CSS 变量（色板）
```

## 11. 非功能性需求

| 项 | 要求 |
|----|------|
| 安全 | 密码 BCrypt；JWT 鉴权；SQL 参数化（MyBatis-Plus / `?` 占位符） |
| 性能 | 商品列表分页（**必须注册 MyBatis-Plus 分页插件**，否则静默失效）；列表页 N+1 查询要消除 |
| 并发 | 确认交易完成时用乐观锁防"一物多卖" |

| 数据一致性 | 标记售出/收藏计数等跨表操作走 `@Transactional`；事务加在 Service 层 |

### 变更原因（这是本项目最重要的一次设计迭代）

**v1.1 的设计有一个致命漏洞**：

> 卖家在线下用微信同时和 3 个买家沟通，回到平台看到 3 条待交易订单 ——
> **他怎么知道刚刚成交的是哪一条？**
>
> 微信昵称和平台昵称大概率不同，订单号更不可能在线下聊天时报出。
> **"卖家从多个订单中选一个"这个动作在现实中无法可靠执行。**
> 选错的后果：真正成交的买家订单未完成，没交易的人却显示已成交。

**v2.0 的回答**：与其做一个会被误操作的系统，不如**不做这个系统**。

平台定位收敛为**信息撮合**：
- 平台负责：商品展示、搜索筛选、**展示联系方式**、记录"谁想要过"
- 用户负责：加微信/QQ 沟通、见面交付、当面付款、自行处理纠纷

**收益**：
1. **零无法自圆其说的分支** —— 没有"退不退款""谁确认""选错人"这类问题
2. **完全贴合校园真实场景** —— 就是"闲鱼看到 → 加微信 → 食堂见面 → 微信转账"
3. **少一张表、少一套状态机、少一个后台模块**
4. **复用行为日志实现"谁想要过"** —— 不需要为咨询单独建表

**代价（已在 §4.2.5 记录）**：无订单数据；无法追踪交易是否真实发生；联系方式直接暴露。这些限制在文档中**明确标注**，不掩盖。
