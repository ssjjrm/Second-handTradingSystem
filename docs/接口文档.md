## 1. 通用约定

### 1.1 统一响应格式

**所有**接口返回：

```json
{
  "code": 200,
  "message": "success",
  "data": { }
}
```

| code | 含义 | 前端处理 |
|:----:|------|----------|
| 200 | 成功 | 正常取 `data` |
| 400 | 参数错误 / 业务校验失败 | 弹 `message` |
| 401 | 未登录 / token 失效 | 清 token，跳登录页 |
| 403 | 无权限 | 弹"无权限访问" |
| 404 | 资源不存在 | 弹提示 |
| 500 | 服务器错误 | 弹通用错误提示 |

> 📌 **HTTP 状态码 = 响应体里的 `code`**（已实现）。
> 例如登录密码错误，返回的是 `HTTP 400` + `{"code":400,"message":"用户名或密码错误"}`，
> 而不是 `HTTP 200` 包一个 400 的 body。
> 好处：看 Network 面板、用 curl、写自动化脚本时，不用解析 JSON 就能判断成败。
> 前端 axios 因此要走 **error 分支**取 `error.response.data.message`（见 `utils/request.js`）。

### 1.2 鉴权

- 登录成功后返回 `token`，前端存 `localStorage`
- 需鉴权的接口在请求头带：

```
Authorization: Bearer <token>
```

**鉴权分组**：

| 分组 | 路径 | 说明 |
|------|------|------|
| 公开 | `/api/auth/register`、`/api/auth/login`、`/api/categories/**`、`GET /api/products/**`（除 contact）、`GET /api/sellers/**` | 游客可访问 |
| 需登录 | 其余 `/api/**` | 需 user 或 admin |
| 需管理员 | `/api/admin/**` | 需 admin |

### 1.3 分页约定

**请求参数**：`page`（默认 1）、`size`（默认 20）

**响应结构**：

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "records": [ ],
    "total": 73,
    "current": 1,
    "size": 20,
    "pages": 4
  }
}
```

### 1.4 枚举定义

**商品状态 `ProductStatus`**

| 值 | 名称 | 说明 |
|:--:|------|------|
| 0 | PENDING | 待审核 |
| 1 | ON_SALE | 在售 |
| 2 | SOLD | 已售出（**卖家手动标记**） |
| 3 | OFF_SHELF | 已下架 |
| 4 | REJECTED | 已拒绝 |

**成色 `ConditionLevel`**（字符串）

`全新` / `几乎全新` / `轻微使用痕迹` / `明显使用痕迹`

**行为类型 `BehaviorType`**

| 值 | 名称 | 触发时机 |
|:--:|------|----------|
| 1 | VIEW 浏览 | 打开商品详情页 |
| 2 | FAVORITE 收藏 | 点「想要」 |
| 3 | **CONTACT 咨询** | **点「联系卖家」查看联系方式** |
| 4 | UNFAVORITE 取消收藏 | 取消「想要」 |

> ⚠️ **本项目没有"订单状态"枚举** —— 平台不产生订单，交易在线下完成。详见 `需求设计文档.md` §4.2。

## 3. 认证模块

### 3.1 注册

```
POST /api/auth/register
鉴权：公开
```

**请求体**

| 字段 | 类型 | 必填 | 校验 | 说明 |
|------|------|:----:|------|------|
| username | string | ✅ | 4~20 字符，唯一 | 登录名 |
| password | string | ✅ | 6~20 字符 | 密码 |
| nickname | string | ❌ | ≤50 字符 | 昵称，留空取 username |
| wechat | string | ❌ | ≤50 字符 | 微信号（**可注册后再填**） |
| qq | string | ❌ | `^[1-9]\d{4,11}$` | QQ 号 |
| phone | string | ❌ | `^1[3-9]\d{9}$` | 手机号（仅账号找回用，**不对外展示**） |

```json
{
  "username": "student04",
  "password": "123456",
  "nickname": "小明",
  "wechat": "xiaoming_2026",
  "qq": "100012345"
}
```

**响应**

```json
{
  "code": 200,
  "message": "注册成功",
  "data": {
    "id": 7,
    "username": "student04",
    "nickname": "小明",
    "wechat": "xiaoming_2026",
    "qq": "100012345",
    "avatar": null,
    "role": "user",
    "status": 1,
    "createTime": "2026-09-22T18:00:00"
  }
}
```

**错误**：`400 用户名已存在`、`400 用户名长度需在 4~20 字符之间`、`400 QQ号格式不正确`

> ⚠️ **响应中绝不包含 password 字段**。
> 💡 微信/QQ **注册时可以不填**，但**发布商品前必须至少填一个**（见 5.4）。

---

### 3.2 登录

```
POST /api/auth/login
鉴权：公开
```

**请求体**：`username`、`password`

**响应**

```json
{
  "code": 200,
  "message": "登录成功",
  "data": {
    "token": "eyJhbGciOiJIUzI1NiJ9...",
    "user": {
      "id": 1,
      "username": "admin",
      "nickname": "管理员",
      "avatar": null,
      "role": "admin",
      "hasContact": true
    }
  }
}
```

> `hasContact` = 是否已填微信号或 QQ。前端据此在点「发布商品」时**提前提示**，而不是等接口报错。

**错误**

| code | message | 场景 |
|:----:|---------|------|
| 400 | 用户名或密码错误 | 用户不存在**或**密码错误（**合并提示，不泄漏账号是否存在**） |
| 403 | 账号已被禁用 | status=0 |

### 3.4 修改资料

```
PUT /api/auth/profile
鉴权：需登录
```

**请求体**（全部可选，只传要改的）

| 字段 | 类型 | 校验 |
|------|------|------|
| nickname | string | ≤50 字符 |
| wechat | string | ≤50 字符 |

### 5.2 商品详情

```
GET /api/products/{id}
鉴权：公开
```

**响应**：在列表字段基础上增加：

| 字段 | 类型 | 说明 |
|------|------|------|
| description | string | 完整描述 |
| updateTime | datetime | 更新时间 |
| isFavorited | boolean | 当前登录用户是否已收藏（**未登录恒为 false**） |
| **canContact** | boolean | 是否可点「联系卖家」 |
| **contactHint** | string | 不可联系时的原因提示 |
| seller | object | 卖家信息（见下，**不含联系方式**） |

```json
{
  "canContact": true,
  "contactHint": null,
  "seller": {
    "id": 2,
    "nickname": "小明",
    "avatar": null,
    "onSaleCount": 5,
    "soldCount": 12
  }
}
```

**`canContact` 计算规则**（前端据此决定按钮可用性）：

| 情况 | canContact | contactHint |
|------|:----------:|-------------|
| 商品在售 + 已登录 + 非自己发布 + 卖家有联系方式 | `true` | `null` |
| 未登录 | `false` | `请先登录后再联系卖家` |
| 是自己发布的商品 | `false` | `这是你发布的商品` |
| 商品已售出/已下架 | `false` | `该商品已不可交易` |
| 卖家未填联系方式 | `false` | `卖家尚未填写联系方式` |

**副作用**：

- 浏览量 `view_count` +1 —— **独立操作，不能因为别的接口调用而虚增**
- 若已登录且**不是自己**的商品，写入 `user_behavior`（type=1 浏览）
- **埋点失败不能影响主流程**（BR-B08）

**错误**：`404 商品不存在`；若商品 status 为 0/3/4 且访问者**不是所有者、不是管理员** → `404`

### 5.3 ⭐ 获取卖家联系方式（核心接口）

```
GET /api/products/{id}/contact
鉴权：需登录
```

**这是整个"信息撮合"模式的核心接口。** 买家靠它拿到卖家的微信/QQ，才能进行线下交易。

**业务校验**

| 校验 | 失败提示 |
|------|----------|
| 已登录 | `401 请先登录后再联系卖家` |
| 商品存在 | `404 商品不存在` |
| 不是自己发布的 | `400 不能联系自己发布的商品` |
| 商品 status=1 | `400 该商品已不可交易` |
| 卖家已填联系方式 | `400 卖家尚未填写联系方式` |

**响应**

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "productId": 12,
    "productTitle": "【九成新】索尼WH-1000XM5 头戴式降噪耳机",
    "sellerId": 2,
    "sellerNickname": "小明",
    "sellerAvatar": null,
    "wechat": "xiaoming_2026",
    "qq": "100012345",
    "tradePlace": "东区食堂门口"
  }
}
```

**副作用**：写入 `user_behavior`（type=3 咨询）。

> ⚠️ **注意：这是 GET 请求但有副作用**。这是一处有意的权衡，**已在文档中标注为已知的设计不规范**：
> - 用 GET 是因为语义上"读取联系方式"
> - 有副作用是因为必须记录咨询行为
> - 严格遵循 REST 应该用 POST。若你希望更规范，改为 `POST /api/products/{id}/contact` 即可，前端改动只有一行。

**前端交互**：点「联系卖家」→ 调本接口 → 弹出**联系方式卡片**：

```
┌─────────────────────────────────┐
│  联系卖家                        │
├─────────────────────────────────┤
│  👤 小明                         │
│                                 │
│  微信号   xiaoming_2026   [复制] │
│  QQ号     100012345       [复制] │
│                                 │
│  📍 交易地点：东区食堂门口        │
│                                 │
│  ⚠️ 请先与卖家确认商品状态和价格， │
│     建议在校内公共场所当面交易     │
└─────────────────────────────────┘
```

### 5.4 发布商品

```
POST /api/products
鉴权：需登录
```

**请求体**

| 字段 | 类型 | 必填 | 校验 |
|------|------|:----:|------|
| title | string | ✅ | 5~100 字符 |
| description | string | ❌ | ≤1500 字符 |
| categoryId | int | ✅ | 必须是存在的**二级分类** |
| conditionLevel | string | ✅ | 枚举四值之一 |
| price | decimal | ✅ | > 0，两位小数 |
| originalPrice | decimal | ❌ | 若填则 ≥ price |
| images | array | ❌ | 最多 9 个 URL |
| brand | string | ❌ | ≤50 字符 |
| tradePlace | string | ✅ | ≤100 字符 |

**业务校验**

| 校验 | 失败提示 |
|------|----------|
| 当前用户已填微信或 QQ | `400 请先完善微信号或QQ号，便于买家联系你` |
| 分类是二级分类 | `400 请选择具体的二级分类` |

**响应**：`{"code":200,"message":"发布成功，等待管理员审核","data":{"id":74}}`

> 新商品 `status=0`（待审核），**不会立即出现在列表里**。

### 5.6 ⭐ 标为已售出

```
PUT /api/products/{id}/mark-sold
鉴权：需登录，且必须是商品所有者
```

**这是"信息撮合"模式下卖家的核心操作**：线下成交后，把商品标记为已售出。

**业务校验**

| 校验 | 失败提示 |
|------|----------|
| 是商品所有者 | `403 无权操作此商品` |
| 商品 status=1 | `400 商品已非在售状态` |
| **乐观锁**：`UPDATE product SET status=2 WHERE id=? AND status=1` | 影响行数 0 → `400 商品已非在售状态` |

**响应**

```json
{
  "code": 200,
  "message": "已标记为售出",
  "data": { "id": 12, "status": 2, "statusText": "已售出" }
}
```

> ⚠️ **这是本项目唯一的并发点**。乐观锁通过 SQL 的 `WHERE status=1` 实现原子性，比"先查再改"可靠。
> 参考项目的 `checkBookLock()` 只是重新查一次状态，没有真正加锁。
>
> **标注为不可逆操作**：标为已售后**不能改回在售**（BR-T06）。前端需二次确认：
> `确定要把《商品名》标记为已售出吗？标记后将不可恢复。`

|------|------|------|

### 10.10 审核开关（开发调试用，**不属于那 35 个业务接口**）

```
GET /api/admin/settings/review          查当前开关
PUT /api/admin/settings/review?enabled=false   关闭审核（发布即上架）
PUT /api/admin/settings/review?enabled=true    开启审核（正式）
鉴权：需 admin
```

**响应**

```json
{
  "code": 200,
  "message": "审核已关闭（测试模式）：新发布的商品直接上架",
  "data": { "enabled": false, "configValue": true, "configKey": "app.review.enabled" }
}
```

| 字段 | 含义 |
|------|------|
| enabled | 当前生效值。`true` = 发布后待审核；`false` = 发布即上架 |
| configValue | `application.yml` 里的值（**重启后会回到它**） |
| configKey | 就是那个配置项的名字，前端拿去提示用户 |

**两种改法**

| 方式 | 命令 / 位置 | 要不要重启 |
|------|------------|:----------:|
| ① 配置文件 | `application.yml` → `app.review.enabled: false` | 要 |
| ② 后台在线切换 | 上面这个 PUT 接口（或后台「商品审核」页顶部的开关） | **不用** |

> ⚠️ **只影响发布时的初始状态**：`false` 时新商品 `status=1`（在售），`true` 时 `status=0`（待审核）。
> 其他业务规则（必须先填微信/QQ、必须选二级分类、原价不低于现价）**全部照旧** ——
> 测试模式不该绕过业务规则。
>
> ⚠️ 运行时切换的值**只存在内存**，重启后端回到配置文件的值。这是刻意的：
> 免得某次调试忘了关，第二天启动还以为自己在正式模式。
> 启动日志里也会显眼地打印当前模式。

**另外**：`GET /api/health` 的响应里多了一个 `reviewEnabled` 字段，
一个 `curl http://localhost:8081/api/health` 就能确认当前是哪个模式。

## 11. 错误码汇总

| code | 场景举例 |
|:----:|----------|
| 400 | 参数校验失败、业务规则不满足（"不能联系自己发布的商品"、"价格必须大于0"、"卖家尚未填写联系方式"） |
| 401 | 未带 token、token 过期、**未登录想看联系方式** |
| 403 | 非管理员访问 `/api/admin/**`、操作他人商品 |
| 404 | 商品/用户不存在、**访问未上架商品（非所有者）** |
| 500 | 未预期的服务器异常（**不返回堆栈**） |

**统一异常处理**：`@RestControllerAdvice` 捕获：

- `MethodArgumentNotValidException` → 400 + 第一条校验失败信息
- `BusinessException`（自定义）→ 400 + 自定义 message
- `Exception`（兜底）→ 500 + "服务器内部错误"
